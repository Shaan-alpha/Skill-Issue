# v0.7.2 prod-certified — 2026-05-21

Methodology: Lighthouse mobile (`lighthouse@latest` via npx) against the actual production URL `https://skill-issue-tau.vercel.app/u/octocat`, headless Chrome, simulated 4G throttling. Five runs after preview-deploy iteration to filter out cold-start outliers.

This is the methodology v0.7.1 should have used from the start. Localhost `next start` measurements are not a valid perf-budget certification surface — confirmed by v0.7.1's localhost-vs-prod gap (94 → 90).

---

## Headline result

| Metric | v0.7.1 prod | **v0.7.2 prod (median)** | Budget | Pass? |
| --- | --- | --- | --- | --- |
| Performance | 90 | **94** / 100 | ≥ 95 | ⚠️ −1 (2 of 5 runs ≥95) |
| LCP | 2,804 ms | **2,773 ms** | ≤ 2,500 | ❌ +273 ms |

| TBT | 228 ms | ~155 ms | — | ✅ |

**CLS structurally fixed** (both shifts eliminated); LCP/TTI improved at the margin but remain over the strict budget; perf score moved from 90 to median 94 with substantial run-to-run variance.

## What landed in v0.7.2

### Fix 1: Loading skeleton matches ResultsView structure ([`loading.tsx`](../../../frontend/src/app/u/[username]/loading.tsx))

Lighthouse on v0.7.1 prod traced the 0.080 anonymous CLS to `div.min-h-screen` (the ResultsView wrapper). Root cause: `loading.tsx` skeleton had **wrong section order** vs the real ResultsView and was **missing three components entirely**:

```
Before (skeleton):  header → big-section → position-bar → badges → score-cards
After  (matches):   header → SaveShareControls → position-bar → badges
                          → big-section → NarrativeCard → scoring-matrix → footer
```

When the backend `fetch` resolved and the page re-rendered, the entire layout reshuffled (big-section moving from slot 2 to slot 5, plus three new sections appearing) causing the deterministic 0.040114 CLS measured 3 times in a row. The other 0.040 was the SiteHeader.

### Fix 2: SiteHeader reserves height ([`site-header.tsx`](../../../frontend/src/components/site-header.tsx))

After fix 1, preview measurements showed CLS halved (0.080 → 0.040) — one shift still remained, same `div.min-h-screen` selector. Root cause: `SiteHeader` had `<Suspense fallback={null}>`, so the header content height was 0 (just py-3 padding ≈ 24 px) until `useSession()` hydrated and the auth pill (h-9 = 36 px) mounted. That ~36 px header growth pushed everything below.

Fix: header gets `min-h-[3.75rem]` (60 px = py-3 + h-9 + bottom border) and the Suspense fallback gets a sized `<div className="h-9" />` placeholder instead of `null`. Same hydrated height before and after `useSession` resolves; CLS dropped to 0 on subsequent preview measurements.

### Fix 3: Dynamic-import NarrativeCard ([`results-view.tsx`](../../../frontend/src/components/results-view.tsx))

NarrativeCard pulls a heavy SSE-streaming client (`EventSource` setup, `useSyncExternalStore` subscription, `localStorage` integration) that only matters once the user reaches the AI section below the fold. Switched to `next/dynamic({ ssr: false })` with a CLS-safe placeholder. Initial bundle dropped 874 → 866 KB uncompressed (−8 KB); larger win is runtime — SSE client setup moves off the initial paint path.

The dynamic-import's effect on perf score was marginal (1-2 points at most). Future LCP work probably needs to identify the actual LCP element on prod (Lighthouse CLI returned `n/a` for the selector in all v0.7.2 runs).

## What didn't land

- **Identifying the prod LCP element.** Lighthouse CLI's `largest-contentful-paint-element` audit returned undefined details for every v0.7.1 and v0.7.2 run. PageSpeed Insights' web UI or Chrome DevTools Performance Insights are the better tools — both deferred to v0.8.0 since they pair with observability work.
- **The strict ≤ 2,500 ms LCP / TTI budget.** Median LCP is 2,773 ms (+273 over), TTI 2,816 ms (+316). Closing those needs an LCP-element-aware optimization which we couldn't make data-driven this slice.

## Decision

**Ship v0.7.2** with these wins documented honestly. The structural CLS fix is permanent; the perf score moved from 90 to 94; remaining LCP gap is ~10% over budget and will be revisited with real-user metrics once v0.8.0's Sentry/PostHog land. The strict-Lighthouse-budget path has diminishing returns vs. the noise floor of localhost-clicking-prod-URL Lighthouse runs.
