## Findings — by severity

### Critical

### Serious

**1 rule violation, 2 occurrences — `/this-does-not-exist` (404 page) only.**

#### `color-contrast` — `/this-does-not-exist`

- **Rule:** `color-contrast` (WCAG 2.1 AA, 1.4.3)
- **Impact:** serious
- **Occurrences:** 2
- **Elements:**
  - `.bg-white` — `<Link href="/">` ("Back to the landing" button)
  - `.border-white\/10` — `<Link href="https://github.com/...">` ("View on GitHub" button)
- **Root cause:** Both links lack an explicit foreground `text-*` class in the dark-style button variants. Headless Chrome renders the page in **light mode** (white background). The browser resolves the link text color to the user-agent default visited/unvisited link color `#9e9eff` (a perceptual-web-safe blue-purple). Against `#ffffff` this yields a contrast ratio of **2.38:1**, well below the required 4.5:1.
  - The `.bg-white` button has `text-black` on the `<Link>` element itself — this is fine. The violation is triggered by the Lucide `<ArrowLeft>` icon or the browser re-computing text; the second button (`.border-white/10`) has **no text color class at all**, relying on inherited/default.
- **Proposed fix (T12):**
  - Add `text-black` (or a high-contrast dark token) to the `.bg-white` button if missing.
  - Add an explicit foreground color to the `.border-white/10` button — e.g., `text-foreground` or `text-white` depending on the intended dark-vs-light context. If the page is dark-themed, ensure the `<html>` carries `class="dark"` so Tailwind applies dark-mode utilities correctly; alternatively use explicit `text-white` on that button.

### Moderate

**3 distinct rule violations across 4 routes, 7 total occurrences.**

#### `landmark-one-main` — `/u/octocat`, `/u/octocat/card`, `/this-does-not-exist`

- **Rule:** `landmark-one-main` (best practice)
- **Impact:** moderate
- **Target:** `html` (document root — page has no `<main>` element)
- **Routes affected:** `/u/octocat`, `/u/octocat/card`, `/this-does-not-exist`
- **Why it matters:** Screen reader users rely on the `<main>` landmark to skip directly to page content. Its absence forces linear navigation through nav/header on every page load.
- **Proposed fix (T12):** Wrap the primary content area of each affected page in a `<main>` element (or add `role="main"` to the existing top-level `<div>`).

#### `page-has-heading-one` — `/u/octocat`, `/u/octocat/card`, `/me`

- **Rule:** `page-has-heading-one` (best practice)
- **Impact:** moderate
- **Target:** `html` (document root — no `<h1>` present in rendered output)
- **Routes affected:** `/u/octocat`, `/u/octocat/card`, `/me`
- **Why it matters:** Screen readers and search engines use the `<h1>` to understand the primary topic of the page. Its absence degrades both a11y and SEO.
- **Proposed fix (T12):**
  - `/u/octocat` — the username + score heading that appears after analysis resolves is a visually prominent element; promote it to `<h1>` (currently likely `<p>` or unstyled `<div>` in the loading skeleton).
  - `/u/octocat/card` — the card title / username display should be an `<h1>`.
  - `/me` — the "Sign in to see your score" or equivalent empty-state heading should be an `<h1>`.

#### `region` — `/this-does-not-exist`

- **Rule:** `region` (best practice, RGAA-9.2.1)
- **Impact:** moderate
- **Target:** `.relative` (the outermost `<div>` in `not-found.tsx`, which is not inside any landmark)
- **Why it matters:** Page content outside landmark regions is inaccessible to screen reader landmark navigation.
- **Proposed fix (T12):** This is resolved as a side-effect of adding `<main>` (see `landmark-one-main` fix above). Wrapping `.relative` in `<main>` eliminates both violations.
