# v0.7.0 — Caching + Performance Design Spec

**Status:** Designed. Implementation pending — TDD plan to follow under `docs/superpowers/plans/`.
**Date:** 2026-05-19.
**Author:** Claude (Opus 4.7) with Shaan.

---

## 1. Goal

Repeat analyses are free and fast. A cold `/analyze/octocat` takes ~8s today (every GitHub round-trip cold). A warm one should drop to **~50ms p95** by serving the previously-computed `Report` straight from Upstash Redis. Each layer below the Report cache (GitHub API responses, narratives, singleflight locks) is a defence-in-depth measure for the cold path.

Bonus: signed-in users today each get their own 5000/hr GitHub rate-limit budget, but on a viral spike the same user could blow it on repeated cold loads. Per-endpoint caching stretches that quota further.

## 2. Locked scope decisions (2026-05-19)

| Decision | Choice | Why |
| --- | --- | --- |
| Provider | **Upstash Redis** | Free tier (10k commands/day, 256MB) is generous; REST-first API is Fluid-Compute-friendly; no TCP keepalive concerns; user is provisioning the account manually (not via Vercel Marketplace) |
| Wire protocol | **REST API** (not Redis protocol) | HTTP-based, no connection pool to manage across cold starts; per-request roundtrip is ~5ms which is well under our budget |
| Client library | **`upstash-redis` (Python, async)** | Official Upstash package; thin wrapper over their REST API; one direct dep |
| Cache layers | **4 layers** — Report, GitHub API, Narratives (shared), Singleflight | See §5 |
| Frontend perf budget | **Deferred to v0.7.1** | Backend caching is the user-facing latency win; Lighthouse / TTI / LCP work is independent and lands cleaner as its own slice |
| Cron re-ingestion | **Deferred to v0.8.0** | Silent cron failures need Sentry first; lands together |
| Failure mode | **Fail-open** — any Upstash error logs and falls through to the live path | The cache is a perf optimisation, not a correctness boundary |

## 3. Architecture (one paragraph)

A new `app/cache/` module owns the Redis client, key helpers, and singleflight locks. Three call-site integrations consume it: `app/github/client.py` wraps individual REST/GraphQL requests; `app/dependencies.py::get_report_for_user` wraps the full Report compute path; `app/narrative/cache.py` swaps its in-process `OrderedDict` for the Redis-backed implementation behind the existing `NarrativeCache` interface. Every cache lookup is non-blocking failure-tolerant — if Upstash is unreachable or returns 5xx, the code logs a warning and falls through to the live path. Tests use a `FakeRedis` stub injected via FastAPI dependency overrides; CI never hits real Upstash.

## 5. Cache layer designs

### 5.1 Layer A — Full Report cache (the user-facing win)

**Key:** `si:v1:report:<lowercased-username>`
**Value:** JSON-serialised `Report` (Pydantic `model_dump_json()`)
**TTL:** 6 hours (`CACHE_REPORT_TTL_SECONDS=21600`)
**Invalidation:** TTL-only for v0.7.0. A manual "Force refresh" button on `/me` lands in v0.8.0 (UI work) and is plumbed via `DELETE /me/cache/<username>` (not in this slice).

Hit path:
1. `get_report_for_user(username)` → `await cache.get_json("report", username.lower())`
2. If hit → return cached `Report` directly (~5ms Upstash RTT)
3. If miss → take singleflight lock, run ingest+score, store result, release lock

Why lowercase the key? GitHub logins are case-insensitive in URLs but case-preserved in the API. Two requests for `Shaan-alpha` and `shaan-alpha` should resolve to the same cache entry.

### 5.2 Layer B — Singleflight lock (cold-path coalescing)

**Key:** `si:v1:lock:report:<lowercased-username>`
**Value:** Random UUID (lock holder's id, used for safe release)
**TTL:** 30 seconds (longer than worst-case ingest+score so the lock outlives a real run)
**Backoff:** Poll the Report cache every 200ms for up to 25s while the lock is held.

Failure modes covered:
- **Lock holder crashes mid-ingest:** TTL expires, next waiter acquires fresh lock.
- **Lock holder finishes but never returned:** Next request finds the Report cache populated on the first poll iteration, skips ingest.
- **Polling waiter times out:** Falls through to the live path (worst case = lockless behaviour, no worse than today).

### 5.3 Layer C — GitHub API response cache

**Key pattern:** `si:v1:gh:<method>:<sha256-of-url-with-params>` (URL hashed for length safety)
**Value:** `{"status": int, "body": <json>}` — preserves 404/422 outcomes so we don't re-fetch a known-bad URL repeatedly
**TTLs per endpoint:**

| Endpoint pattern | TTL | Why |
| --- | --- | --- |
| `GET /users/{u}` | 1 hour | Profile metadata barely changes |
| `GET /users/{u}/repos` | 15 min | New pushes show up quickly |
| `GET /repos/{o}/{r}/languages` | 1 hour | Language stats are stable |
| `GET /repos/{o}/{r}/contents` (root only) | 30 min | README/CI presence shifts slowly |
| `GET /repos/{o}/{r}/commits` | 5 min | Hot — consistency scorer depends on freshness |
| GraphQL POST `/graphql` | 15 min | Composite query, key includes the variables hash |

Hit path: in `GitHubClient._request`, before the actual HTTP call:
```python
if self._cache and method == "GET":  # POSTs to /graphql also cacheable; key includes body
    cached = await self._cache.get_json("gh", _gh_cache_key(method, url, params, body))
    if cached is not None:
        return _Response(status_code=cached["status"], json_=cached["body"])
```

Non-200 responses are NOT cached for retry-able statuses (429, 5xx) — only 200, 404, 422 are. Rate-limit (403) responses pass through unaltered so the existing backoff logic still fires.

### 5.4 Layer D — Narrative cache + shared daily budget

**Narrative cache key:** `si:v1:narrative:<username>:<scores_hash>:<mode>` (matches the existing tuple)
**Value:** the rendered narrative text
**TTL:** 24 hours

**Daily budget key:** `si:v1:budget:narrative:<UTC-yyyy-mm-dd>`
**Value:** integer counter (Redis `INCR`)
**TTL:** 25 hours (lazy expiry — fresh key gets created on first INCR per day)

The existing `NarrativeCache` and `DailyBudget` classes get a `redis: RedisCache | None` parameter. When Redis is configured, all reads/writes go to Upstash; otherwise the in-process fallback is preserved for tests. The `NarrativeService` orchestration in `narrative/service.py` doesn't change — it talks to the same interface.

## 6. Failure handling

Every cache operation follows this pattern:

```python
async def get_json(self, namespace: str, key: str) -> Any | None:
    try:
        raw = await self._redis.get(self._build_key(namespace, key))
    except Exception:
        logger.warning("Upstash GET failed for %s:%s", namespace, key, exc_info=True)
        return None
    if raw is None:
        return None
    try:
        return json.loads(raw)
    except json.JSONDecodeError:
        logger.warning("Cached value for %s:%s is not JSON; ignoring", namespace, key)
        return None
```

The cache is **never** a correctness boundary. Any failure logs and falls through.

For the singleflight lock specifically, if Redis is unreachable when trying to acquire, we proceed without locking (logs a warning). Worst case = no coalescing, which is no worse than today.

## 7. Settings additions

```python
class Settings(BaseSettings):
    ...
    # v0.7.0 — caching
    upstash_redis_rest_url: str | None = None
    upstash_redis_rest_token: str | None = None
    cache_report_ttl_seconds: int = 21_600    # 6 hours
    cache_default_ttl_seconds: int = 900      # 15 minutes — for layers that don't pick a specific TTL
```

When `upstash_redis_rest_url` is unset, `get_cache()` returns `None` and every cache integration short-circuits. Locally, agents/devs can run without Upstash configured and get today's behaviour unchanged.

**Env vars to add in Vercel (Preview + Production):**
- `UPSTASH_REDIS_REST_URL` — sensitive
- `UPSTASH_REDIS_REST_TOKEN` — sensitive

Both pasted from the Upstash console. The user creates the DB outside Vercel; we paste credentials into Vercel manually (no Marketplace integration).

## 8. Testing strategy

- **No live Upstash in CI.** A `FakeRedis` stub in `tests/cache/conftest.py` implements `get/set/setex/del/incr/setnx/expire` with a dict + threading lock. Async surface matches `upstash_redis.asyncio.Redis`.
- **`fake_cache` fixture** wraps the stub in a `RedisCache` and returns it.
- **FastAPI dependency override** in `tests/conftest.py` makes every test-client call see the fake cache.
- **Cache-layer unit tests:**
  - Round-trip set + get
  - TTL expiry honoured (FakeRedis tracks deadlines)
  - Namespace prefix collisions don't bleed
  - Fail-open: GET that raises returns `None`
- **Singleflight unit tests:**
  - First caller holds, second caller waits + finds populated cache
  - Lock TTL expires → next caller acquires fresh
  - Redis unreachable → caller proceeds without lock (logs warning)
- **Integration tests (existing `test_analyze_e2e.py` etc):** add a second call after the first to assert the second is a cache hit (mock the GitHub client and assert `gh.get_user.call_count == 1` after two `/analyze/{user}` requests).

Target: ~25 new tests across `tests/cache/` + 4 integration assertions in existing files. Total backend test count: 186 (current) → ~215.

## 9. Performance budget

| Metric | Target |
| --- | --- |
| Warm `/analyze/{user}` p95 | ≤ 200ms end-to-end (excl. network from client) |
| Cold `/analyze/{user}` p95 | Unchanged from today (~8s) |
| GitHub API call reduction on warm path | ≥ 95% (every GH call cached after first run) |
| Narrative cache hit latency | ≤ 50ms (single Redis GET + JSON parse) |

The exit criteria measure on the deployed Vercel preview, not local dev (local Upstash RTT is closer to ~10-20ms because of geography; production is co-located).

## 11. Out of scope (do not silently expand)

- Frontend perf budget / Lighthouse work — v0.7.1 patch.
- Cron-driven background re-ingestion — v0.8.0 (paired with Sentry).
- User-facing "Force refresh" button + `DELETE /me/cache/<u>` route — v0.8.0 (UI work).
- Cache stampede protection beyond singleflight (e.g. probabilistic early refresh) — premature; revisit if real load shows stale-hit cliffs.
- Multi-region Redis replication — Upstash global has one ~25ms RTT from us-east; not worth complicating until measured.
- Rate limiting (per-IP, per-user) — v0.9.0 Beta hardening.
- Local-dev Redis docker fallback — agents and devs run without Upstash configured; the in-process fallback is the local-dev story.

## 12. Known imprecisions

- **Reanalysis on stale data within TTL.** A user who pushes a big commit at minute 1 won't see the new score until the 6-hour TTL expires. Acceptable for v0.7.0; the v0.8.0 manual-refresh button is the fix.
- **`upstash-redis` Python package vs DIY httpx.** I'm choosing the library for safety (handles auth headers, retries, error mapping). It's ~one extra dep + ~80kB. If the dep grows tiresome later we can swap to a 50-line DIY wrapper without changing call sites.
- **Token-scoped GitHub responses are not key-discriminated.** A signed-in user's GH token returns the same public data as the project token (`public_repo` scope), so this is fine for `/users` and `/repos` endpoints. If we ever add private-data scopes, the cache key needs to include a token-scope fingerprint.
- **Singleflight wait time is 25s.** A pathological GitHub-side stall could mean a waiter times out before the lock holder finishes. The waiter then falls through to a live ingest (no worse than today). Worth memorising if we ever see double-ingest in logs.
