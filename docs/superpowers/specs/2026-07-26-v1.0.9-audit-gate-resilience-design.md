# v1.0.9 — Audit-gate resilience — Design

**Date:** 2026-07-26
**Slice:** v1.0.9
**Status:** design approved, awaiting implementation plan

---

## 1. Goal

Stop an advisory-registry outage from converting a security gate into a repo-wide hard blocker — without weakening the gate's ability to catch real advisories.

**Triggering incident (2026-07-26).** `https://registry.npmjs.org/-/npm/v1/security/advisories/bulk` began returning HTTP 200 with a gzip body that npm could not decode. `npm audit` exited 1. Because the CI step gates on exit code alone, the `Frontend (lint + test + build)` job failed on every pull request — including PR #43, a docs-only change touching no dependency. Reproduced in CI twice and locally, against both `/frontend` and the repo-root project, so the cause is registry-side and global.

The backend has the identical weakness: `uvx pip-audit -r requirements.txt` raises `ServiceError` / `ConnectionError` when PyPI or OSV is unreachable, and the step gates on exit code alone.

## 2. Scope

**In scope**
- `npm audit` gate in the frontend CI job.
- `pip-audit` gate in the backend CI job.
- A shared, unit-tested classification module used by both.

**Out of scope (deliberate)**
- Restoring `--audit-level=high`. Still blocked upstream: latest Next.js is 16.2.12, inside the vulnerable advisory range (fix `>16.3.0-preview.7`, unreleased). This design makes the restore a one-argument change in `ci.yml`.
- Triaging the 25 open Dependabot alerts / 14 open Dependabot PRs. Several are major-version jumps (`typescript` 5→7, `eslint` 9→10, `@types/node` 20→26, `actions/checkout` 4→7) that need real review; that is its own slice.
- `actions/dependency-review-action` (the SI-37 PR gate). It is GitHub-hosted, a separate failure domain, and was not implicated.

## 3. Design

### 3.1 The discriminator

Both tools share one property: **on a transport failure, neither emits a valid results document.** The exit code is `1` in both the outage case and the real-advisory case, which is exactly why the current gate cannot tell them apart. The parsed shape can.

| | Outage | Real advisory |
| --- | --- | --- |
| `npm audit --json` | `{"message": "...", "error": {...}}` — no `metadata` | `{"vulnerabilities": {...}, "metadata": {...}}` |
| `pip-audit -f json` | no JSON; `ServiceError` / `ConnectionError` | `{"dependencies": [...]}` |
| exit code | `1` | `1` |

### 3.2 Four verdicts

"Pass on outage" must not degrade into "pass on anything we don't understand." If `pip-audit` dies because `requirements.txt` is malformed, stdout also fails to parse — and treating that as an outage would wave a genuine breakage through. That is the same silent-green failure mode as the v1.0.8 `config` job, which reported success while typechecking nothing.

The gate therefore forgives only failures it can **positively identify** as transport:

| Verdict | Condition | Exit |
| --- | --- | --- |
| `CLEAN` | Results document parsed; nothing at/above threshold | 0 |
| `FINDINGS` | Results document parsed; advisories at/above threshold | 1 |
| `SERVICE_UNAVAILABLE` | No results document **and** stderr/stdout matches a known transport signature | 0 + `::warning::` |
| `ERROR` | No results document and **no** transport signature | 1 |

The `ERROR` row is the safety property. Anything unexplained fails loudly.

### 3.3 Transport signatures

Matched case-insensitively against combined stdout + stderr:

- `audit endpoint returned an error`
- `invalid json response body`
- `ConnectionError`, `ServiceError`
- `ETIMEDOUT`, `ECONNRESET`, `ENOTFOUND`, `EAI_AGAIN`
- HTTP `429`, `500`, `502`, `503`, `504`

The 2026-07-26 npm incident matches the first two, and emits them on **both** streams (stdout carries a top-level `error` key; stderr carries `npm error audit endpoint returned an error`), so detection is redundant.

### 3.4 Module shape

Location: `backend/tools/audit_gate.py`, tests at `backend/tests/tools/test_audit_gate.py`.

`app/` is the deployed FastAPI package, so CI tooling does not belong in it. `backend/tools/` inherits the existing pytest + uv setup at no cost. The consequence — the *frontend* CI job invokes a script living under `backend/` — is intentional, not an accident; a repo-root `tools/` would be conceptually tidier but would require standing up a second pytest configuration and another CI job, which this slice does not warrant.

```python
classify(stdout: str, stderr: str, returncode: int, ecosystem: str, threshold: str) -> Verdict
run_gate(ecosystem: str, threshold: str, requirements: str | None = None,
         attempts: int = 3, sleep=time.sleep) -> int
```

`requirements` is pip-only (the `-r` target) and ignored for npm. `sleep` is injected so retry tests run instantly.

The subprocess each ecosystem shells out to:

- npm — `npm audit --omit=dev --json`
- pip — `uvx pip-audit -r <requirements> -f json`

Note the gate always requests **JSON** and does its own threshold comparison; it no longer delegates the pass/fail decision to `--audit-level`.

- `classify` is **pure** — no network, no clock, no subprocess. All reasoning lives here, so every interesting case is a plain unit test against a captured payload.
- `run_gate` is a thin wrapper: invoke, classify, retry on `SERVICE_UNAVAILABLE`, map the final verdict to an exit code.

**Stdlib only** (`subprocess`, `json`, `sys`, `time`, `argparse`, `re`). The frontend job then needs no Python setup step — only the `python3` already present on `ubuntu-24.04`.

### 3.5 Per-ecosystem parsing

**npm** — a results document is JSON with `metadata.vulnerabilities`. A top-level `error` key, or absent `metadata`, means no results document. Severity counts at or above `threshold` (`low` < `moderate` < `high` < `critical`) produce `FINDINGS`.

**pip-audit** — a results document is either `{"dependencies": [...]}` or a bare array; the shape varies by version, so both are accepted. Any dependency with a non-empty `vulns` list produces `FINDINGS`. `pip-audit` has no severity threshold, so `threshold` is ignored for this ecosystem — stated explicitly so the asymmetry is not read as an oversight.

### 3.6 Retry and loudness

- 3 attempts, 5s then 15s backoff. Retry **only** on `SERVICE_UNAVAILABLE`; `FINDINGS` and `ERROR` fail fast. Worst case adds ~20s.
- The outage path emits a GitHub `::warning::` annotation so it surfaces in the PR checks UI rather than only in the log body.
- `FINDINGS` prints the advisory summary so the failure is actionable.
- The sleep function is injected so tests exercise retry logic with no real delay.

## 4. Testing

TDD. `classify` being pure makes each case a payload in, a verdict out.

| # | Case | Expected |
| --- | --- | --- |
| 1 | npm outage — captured live payload from 2026-07-26 | `SERVICE_UNAVAILABLE` |
| 2 | npm clean | `CLEAN` |
| 3 | npm critical vuln, threshold `critical` | `FINDINGS` |
| 4 | npm moderate only, threshold `critical` | `CLEAN` |
| 5 | npm high vulns, threshold `high` | `FINDINGS` |
| 6 | pip-audit `ConnectionError` on stderr | `SERVICE_UNAVAILABLE` |
| 7 | pip-audit clean, `{"dependencies": [...]}` | `CLEAN` |
| 8 | pip-audit legacy bare-array shape | parsed correctly |
| 9 | pip-audit with vulns | `FINDINGS` |
| 10 | garbage stdout, no transport signature | `ERROR` |
| 11 | empty stdout, no transport signature | `ERROR` |
| 12 | `run_gate` retries N times then warns, exits 0 | injected sleep |
| 13 | `run_gate` does not retry on `FINDINGS` | fails fast |
| 14 | `run_gate` does not retry on `ERROR` | fails fast |

Cases 10 and 11 are the regression test for "unknown failure silently passes." Case 5 proves the threshold knob works, which is the mechanism for the deferred `high` restore.

Fixture note: case 1 uses the payload captured live during the incident (stdout and stderr both preserved), not a hand-written approximation.

## 5. CI wiring

Both steps collapse to one line each:

- frontend job (working directory `frontend`): `python3 ../backend/tools/audit_gate.py npm --threshold critical`
- backend job (working directory `backend`): `uv run python tools/audit_gate.py pip --requirements requirements.txt`

The `--threshold critical` argument is the entire restore path. When Next.js ships a patched release, it becomes `--threshold high` — no code change, no new tests.

The existing `TEMPORARY (2026-07-24)` comment block in `ci.yml` explaining the lowered threshold is preserved and updated to point at the argument rather than the inline `npm audit` flag.

## 6. Version-plan impact

New slice **v1.0.9** in `PLAN.md`, following v1.0.8. Version constants bumped in all three places (`backend/app/settings.py`, `frontend/package.json`, `frontend/src/lib/site.ts` — the drift guard added in v1.0.7 enforces agreement). `CHANGELOG.md` gains a `[1.0.9]` section.

`CHANGELOG.md` heading discipline matters here: `release.yml` builds release notes by matching `## [<version>]`, so a missing heading is release-blocking for that version. This was hit on 2026-07-26 when the `[1.0.6]` heading was found absent.

## 7. Implementation order (for writing-plans)

1. Capture fixtures — live npm outage stdout/stderr; synthesize the npm clean / critical / moderate / high and pip-audit clean / vulns / legacy-array payloads.
2. `classify` for npm (tests 1–5), then pip (tests 6–9), then the `ERROR` guard (tests 10–11).
3. `run_gate` retry behaviour with injected sleep (tests 12–14).
4. CLI wrapper — `argparse`, `::warning::` emission, exit-code mapping.
5. Wire both `ci.yml` steps; preserve and update the threshold comment block.
6. Version bump, `CHANGELOG.md` `[1.0.9]`, `PLAN.md` row + exit criteria, `docs/PROGRESS_LOG.md` entry.

## 8. Exit criteria

- [ ] `classify` unit tests pass for all 14 cases, including the two `ERROR` guards.
- [ ] Backend `ruff` clean; `pytest -q` green with the new tests added to the existing suite.
- [ ] Frontend `lint` + `tsc` + `test:run` + `build` clean.
- [ ] With npm's advisories endpoint still failing, the frontend CI job **passes with a visible `::warning::`** rather than failing.
- [ ] A deliberately-injected `FINDINGS` payload still fails the job (the gate is not merely disabled).
- [ ] A deliberately-malformed `requirements.txt` produces `ERROR` and fails the job.
- [ ] All three version constants at `1.0.9`; `CHANGELOG.md` `[1.0.9]` heading present and matched by `release.yml`'s extractor.
- [ ] PR reviewed; CI green; prod deploy verified.
- [ ] Tag `v1.0.9`; release. *(Paused for operator go-ahead per the standing slice workflow.)*
