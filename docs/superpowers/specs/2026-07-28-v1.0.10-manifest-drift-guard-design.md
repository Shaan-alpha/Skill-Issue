# v1.0.10 — Dependency-manifest drift guard — Design

**Date:** 2026-07-28
**Slice:** v1.0.10
**Status:** design approved, awaiting implementation plan

---

## 1. Goal

Make a mismatch between `backend/pyproject.toml`, `backend/uv.lock` and `backend/requirements.txt` fail CI deterministically, instead of surfacing by accident.

## 2. Why

The backend has a three-file dependency chain and nothing verifies either link:

```
pyproject.toml  ──►  uv.lock  ──►  requirements.txt
   (declared)         (resolved)      (exported)
```

Dependabot PR #45 broke the second link on 2026-07-27. It bumped the transitive `pydantic-core` to `2.47.0` while leaving `pydantic` at `2.13.4`, which pins `pydantic-core==2.46.4` **exactly** — an unsatisfiable combination. Its two files did not even agree with each other: `uv.lock` said `2.48.0`, `requirements.txt` said `2.47.0`.

The root cause is structural rather than a one-off. `requirements.txt` is **generated** (`uv export`), so editing individual pinned lines in it bypasses the resolver that makes those pins coherent. Any future Dependabot PR touching a transitive pin can reproduce it.

Nothing detected this as drift. It surfaced only because `pip-audit` happened to fail resolving the result, reporting `ResolutionImpossible`. That is the same failure shape v1.0.9 was built to remove: **a check reporting the wrong thing for the wrong reason.** A drifted manifest that still happens to resolve would pass silently today.

There is precedent for silent drift here. In v0.8.5 `requirements.txt` was found to be missing 9 of 15 direct dependencies and had been that way for months, undetected.

## 3. Scope

**In scope**
- A CI step asserting both links of the chain.
- Correcting two comments that currently describe `requirements.txt` incorrectly.
- Version bump to `1.0.10` plus the usual slice housekeeping.

**Out of scope**
- Removing `requirements.txt` and generating it at audit time. This would make drift structurally impossible rather than merely detected, and was considered. Rejected for this slice: it depends on `requirements.txt` genuinely not being read at install time, which the evidence supports but does not prove, and the conservative option costs little.
- Auditing `uv.lock` directly. `pip-audit --locked` expects a PEP 751 `pylock.toml` and does not read `uv.lock` — verified 2026-07-28: `ERROR:pip_audit._cli:no lockfiles found in .`
- Any frontend equivalent. `package-lock.json` is maintained by npm itself and `npm ci` already fails on a manifest/lock mismatch.

## 4. Design

### 4.1 The check

One step, no new code — composed from native tooling:

```yaml
- name: Dependency manifests in sync
  run: |
    uv lock --check
    uv export --no-hashes --no-dev --format requirements-txt -o requirements.txt
    git diff --exit-code -- requirements.txt
```

- **`uv lock --check`** covers `pyproject.toml → uv.lock`. Native flag, exact, no output parsing.
- **regenerate + `git diff --exit-code`** covers `uv.lock → requirements.txt`.

Both commands rely on the `backend` job's existing `defaults.run.working-directory: backend`, so the bare `requirements.txt` path resolves to `backend/requirements.txt`. If the step is ever moved to a job without that default, the paths must be qualified.

### 4.2a Line endings

The repo has no `.gitattributes`. On the Linux runner Git leaves content as-is and `uv export` writes LF, so the comparison is LF-to-LF. On Windows, where contributors commonly have `core.autocrlf=true`, Git normalises to LF in the index before diffing, so the check does not false-positive there either — confirmed while validating the design on Windows, where the drifted-file test produced a one-line diff rather than a whole-file one.

### 4.2 Why regenerate in place rather than diff a temp file

`uv export` writes a two-line header echoing the exact command that produced the file, including the `-o` argument:

```
# This file was autogenerated by uv via the following command:
#    uv export --no-hashes --no-dev --format requirements-txt -o requirements.txt
```

Exporting to a temp path therefore produces a file that differs on line 2 by construction, so a naive `diff` reports drift on every run. Regenerating **in place** with the byte-identical command the committed file already records sidesteps this entirely: the header matches, and any remaining difference is real. No normalisation, no `tail -n +3`, nothing to get subtly wrong.

The working tree is ephemeral in CI, so rewriting the file there is harmless. Run locally it repairs the drift, which is the desired fix anyway.

### 4.3 Placement

New step in the `backend` job, immediately **before** `pip-audit`. Ordering matters: the audit should run against a manifest already proven to match the lock, rather than against a file that may not describe the resolved dependency set.

### 4.4 Failure output

`git diff --exit-code` prints a standard diff naming the offending package, e.g.

```
-sqlalchemy==2.0.49
+sqlalchemy==2.0.51
```

which tells the reader both what drifted and what it should be. No custom error formatting needed.

## 5. Doc corrections included

Two comments currently assert that `requirements.txt` is the deploy manifest. It is not — Vercel resolves through `pyproject.toml` + `uv.lock`, which v0.8.5 demonstrated empirically when a `requirements.txt` missing 9 of 15 direct dependencies left production unaffected. `docs/DEPLOY.md:164` already states this correctly; the other two contradict it:

| File | Currently says | Should say |
| --- | --- | --- |
| `.github/workflows/ci.yml:70` | "the exported requirements.txt (what actually deploys)" | it is the pip-audit input; Vercel installs from `pyproject.toml` + `uv.lock` |
| `backend/.vercelignore:3` | lists `requirements.txt` among "only runtime code needs to ship" | it ships but is not the install manifest |

These are in scope because the next person debugging this chain will read them first, and both currently point away from the truth.

## 6. Testing

No unit tests. There is no bespoke logic to test — the step composes two native commands, and a test would only assert that `uv` and `git` behave as documented.

Verification is behavioural, and both scenarios were run against the real repo on 2026-07-28 before this design was written:

| Scenario | Expected | Observed |
| --- | --- | --- |
| Clean tree | both checks pass | `uv lock --check` OK; `git diff` exit 0 |
| Committed drift (`sqlalchemy` 2.0.51 → 2.0.49, mimicking #45) | fail, naming the package | `git diff` exit 1, reported `-sqlalchemy==2.0.49 / +sqlalchemy==2.0.51` |

The drift scenario must be committed, not merely written to the working tree: the regenerate step overwrites an uncommitted edit before `git diff` runs, so a working-tree-only test heals the drift and passes vacuously. This was hit while validating the design and is recorded here so the implementation test does not repeat it.

`uv lock --check` **passed** on the drifted commit, confirming the two checks cover genuinely independent links and neither is redundant.

## 7. Version-plan impact

Ships as **v1.0.10**, consistent with v1.0.9 — also CI-only — carrying a version and a CHANGELOG entry. Three constants move together: `backend/app/settings.py`, `frontend/package.json`, `frontend/src/lib/site.ts`. The v1.0.7 drift guard at `frontend/src/lib/site.test.ts` fails if the latter two disagree.

The CHANGELOG entry should be honest that this has no user-visible effect, rather than manufacturing user-facing framing for an internal check.
