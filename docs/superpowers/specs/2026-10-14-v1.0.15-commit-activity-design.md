# v1.0.15 — Commit activity from GitHub's contribution data (design)

**Date:** 2026-10-14 · **Status:** design approved section by section in brainstorming (2026-10-14); this written spec awaits the operator's review · **Slice type:** patch (scoring)

## 1. Why

This slice fixes S18 from the v1.0.14 deep audit. Consistency (10 points) and Learning Trajectory's two-year check read commit days from REST commit lists. Those lists cover the default branch of the user's own ten repos with the newest `updated_at`, 100 commits each. Two blind spots follow.

- **Org work is invisible.** gaearon scores 0/10 for Consistency, because 17 commit days are visible. GitHub records 626 commits by him in the last year, spread across 39 public repos. 31 of those repos belong to someone else, such as `react/react` and `vercel/next.js`.
- **`updated_at` moves when a repo gains stars.** gaearon's ten "most recently updated" repos were last pushed between 2015 and 2019, and all of them showed yesterday as their update date.

Re-ordering the sample by `pushed_at` was measured and does not fix this. Its effects run both ways: sindresorhus +3, tj +4, Shaan-alpha −3. The problem is the data source, not the order.

## 2. Operator decisions (2026-10-14)

| Question | Decision |
| --- | --- |
| What activity counts | **Public commits across all repositories:** own, org and other people's, from GitHub's contribution data. Private repositories are excluded. Their contributions depend on whose token asks, and the report cache is keyed by username alone (the same reason v1.0.14 added `is:public` to the PR search). |
| Consistency rules | **Unchanged.** Only the data changes. Recalibrating is a separate decision, if the impact table shows the bars saturating. |
| Repo sampling | **Hybrid.** The repo list stays one page of 100 ordered by `updated_at`, so star signals still see popular repos. Within it, the 20 most recently *pushed* non-forks get root listings and languages, and the 5 most recently pushed give the commit-message sample. |
| Approach | **One contributions query** with two windows, falling back to the REST sample when GitHub can't answer it. |
| Version | **This slice is v1.0.15.** The toolchain majors, still only proposed, move to v1.0.16. |

| --- | --- | --- | --- | --- | --- |

- The query cost **1 GraphQL point** for every account, and none hit `RESOURCE_LIMITS_EXCEEDED`. That includes the two hyper-active accounts.
- In `commitContributionsByRepository`, `contributions.totalCount` is the repo's commit count. Each node is one day with a `commitCount` (gaearon's 263 `conway-refinement` commits fall on 13 days). Nodes come newest first, and the date part of `occurredAt` labels the day.
- Each repository carries `isPrivate`, so the data can be filtered to public repos. The contribution calendar cannot be filtered that way.

## 4. Design

### 4.1 One query, two windows

```graphql
query CommitActivity($login: String!, $from: DateTime!, $to: DateTime!, $priorFrom: DateTime!) {
  user(login: $login) {
    lastYear: contributionsCollection(from: $from, to: $to) {
      commitContributionsByRepository(maxRepositories: 100) {
        repository { isPrivate }
        contributions(first: 100) { totalCount pageInfo { hasNextPage } nodes { occurredAt } }
      }
    }
    priorYear: contributionsCollection(from: $priorFrom, to: $from) {
      commitContributionsByRepository(maxRepositories: 100) {
        repository { isPrivate }
        contributions(first: 1) { nodes { occurredAt } }
      }
    }
  }
}
```

The windows are whole UTC days, as in v1.0.14, so the cache key stays the same all day. `to` is tonight's UTC midnight, `from` is `to − 365 days`, and `priorFrom` is `from − 365 days`. A `to` in the future is accepted; this was verified live in v1.0.14.

### 4.2 Mapping onto the Profile

The scorers keep reading the same Profile fields:

- **`commit_dates`** holds the public day labels from both windows, each a UTC-midnight datetime.
- **`commit_history_complete_since`**: among `lastYear` repos with `hasNextPage`, take each repo's oldest returned day, then the latest of those. If no page was cut off, it is `None`. The meaning is the same as today: "every commit day after this is visible." The existing truncation-aware dry-spell rule then applies unchanged. torvalds' kernel tree is the case it exists for.
- **New `substantial_repo_count: int | None`** counts public `lastYear` repos with 10 or more commits. It is `None` when the activity came from the fallback.
- **New `commit_activity_scope: Literal["all_public_repos", "own_recent_repos"]`** defaults to `"all_public_repos"`. Ingestion sets `"own_recent_repos"` when it falls back.
- **`commit_subjects`** keeps coming from the REST commit sample (§4.4).

### 4.3 What goes

- Ten REST commit lists become five (§4.4).
- The older-commit probe (`per_page=1`, `until`): the `priorYear` window answers that question.
- The `ContributionRepos` query and `GitHubClient.get_contribution_repo_count`. The Staff+ unlock copies `substantial_repo_count` into `cross_repo_contribution_count` without a request. This also stops private repos from counting toward it.

### 4.4 Sampling (hybrid)

- `list_repos` is unchanged: `sort=updated`, one page of 100. `Profile.repos` keeps the list order, and `repo_list_capped` keeps its meaning.
- **Root listings and languages** go to the `ROOT_CONTENT_LIMIT` (20) non-forks with the newest `pushed_at`. Ties keep list order. `root_inspected` marks exactly those repos.
- **The commit-message sample** comes from the 5 non-forks with the newest `pushed_at`. Each is one REST page of up to 100 of the user's own commits, since `priorFrom` (two years back, as today). Its commit days are the fallback's data.

### 4.5 Errors

- `GitHubRateLimited` and `GitHubCallCapExceeded` from `CommitActivity` fail the analysis (503), as everywhere since v1.0.14.
- Anything else falls back. That covers an exception, a body without `user`, and a `lastYear` that is null. The fallback derives `commit_dates` and `commit_history_complete_since` from the REST sample, using today's logic over 5 repos. It sets `commit_activity_scope = "own_recent_repos"` and leaves `substantial_repo_count = None`.
- If `lastYear` is present but `priorYear` is null, `lastYear` is used, and Learning Trajectory may miss the year before. That is acceptable for a partial answer, and no score is invented.

### 4.6 Scoring and evidence

- **Consistency rules are unchanged:** commits in each of the last 3 calendar months (4), no gap of 60 days or more (3), and 30 or more commit days (3).
  - The `high_volume` row reads "Committed on N days in the last year across public repositories" when `commit_activity_scope == "all_public_repos"`, and keeps today's wording otherwise.
  - On fallback, a context row with weight 0 is added: signal `commit_activity_scope`, detail "Counted from the 5 most recently pushed own repositories only: GitHub didn't return activity across all repositories".
- **Learning Trajectory is unchanged.** "Commits in each of the last two years" now sees both windows.
- **Cross-repo breadth** is still a Staff+ context row with weight 0. It is now computed from public repos only, and it is absent on fallback.
- **README evidence** names the new scope: "…of the 20 most recently pushed non-fork repos have READMEs" (§4.4). The licence row keeps "most recently updated" for a capped list, because the list itself is still ordered by update.
- **The narrator:** the few-shot examples in `app/narrative/prompts.py` that quote the changed evidence wording are updated, and the prompt snapshots are regenerated.
- **Report cache:** `REPORT_SCHEMA_VERSION` 2 → 3.

## 5. Testing and verification

**Ingestion, test-first** (each test fails against v1.0.14 code first):

- Private repositories contribute no days.
- Day nodes from both windows map into `commit_dates`.
- A cut-off `lastYear` page sets `commit_history_complete_since` to the latest of the cut-off repos' oldest days.
- `substantial_repo_count` counts public repos with 10+ commits.
- Rate limits and the call cap raised by `CommitActivity` fail the analysis.
- Any other failure falls back to the 5-repo REST sample with `commit_activity_scope = "own_recent_repos"`.
- Root listings, languages and the commit sample follow `pushed_at` within the update-ordered list.
- The cache key repeats within a UTC day.

**Scoring:**

- The existing Consistency and Learning Trajectory tests pass unchanged, which proves the rules did not move.
- New tests cover the `high_volume` wording, the fallback context row, the README scope wording, and the Staff+ copy needing no request.

**Integration:**

- The end-to-end and cache tests route `CommitActivity`.
- The full suite runs against a local Postgres 18 with no skips.
- One fresh-context reviewer and a skeptic go over the branch before the PR.

**Live, before merge:**

- The §6 table is re-measured on the branch, back to back with `main`, and the operator approves it.
- The new evidence wording is checked in Chrome at 1440/1024/768/390.

**After merge:** a production smoke (`/health` 1.0.15, a live analysis showing all-repository commit days, the narrator streaming), then the pause before the tag.

## 7. Out of scope

- **Paging through repos with more than 100 commit days in the year.** 100 or more days clears every Consistency bar, and `commit_history_complete_since` already handles the unseen part.
- **Private contributions and the contribution calendar** (§2).
- **Recalibrating the Consistency thresholds** (§2).
- **Commits on non-default branches.** GitHub's contribution rules count default-branch commits, as the REST lists did.
- **Repositories beyond the 100 per window** (`maxRepositories`). sindresorhus reaches exactly 100; days in a 101st repo almost certainly overlap days already seen.
- **The double `/me` session request (O2) and the tier bar's "N/100" sub-rank label (U5)**, which are tracked separately.
