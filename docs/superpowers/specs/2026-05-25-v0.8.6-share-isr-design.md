# v0.8.6 — `/share/[slug]` ISR + on-demand `revalidateTag` design spec

**Status:** Designed. Implementation plan to follow under `docs/superpowers/plans/`.
**Date:** 2026-05-25.
**Author:** Claude (Opus 4.7) with Shaan.

---

## 1. Goal

Public `/share/[slug]` pages render from a per-slug cache instead of `cache: "no-store"`, so visiting a viral shared link doesn't fan out to the backend on every hit. Revocation (or re-share) must bust the cache **synchronously** so a revoked slug returns 404 on the next request — no TTL window of stale public exposure.

This closes the v0.7.1 deferral: ISR on `/share/[slug]` was punted because `export const revalidate = N` leaves a revocation gap of up to N seconds. Tag-based invalidation removes that gap entirely.

## 2. Locked scope decisions (2026-05-25)

| Decision | Choice | Why |
| --- | --- | --- |
| Cache API | **Next 16 Cache Components (`'use cache'` + `cacheTag`)** | The recommended path per the Vercel 2026-02-27 knowledge update. `unstable_cache` is being deprecated; Cache Components are GA on Next 16. Tag-based invalidation is a first-class primitive. |
| Cache scope | **Per-slug, not per-page-render** | Tag the *fetched JSON* (the `loadShared(slug)` call), not the page itself. Lets us bust just the data and let React re-render. |
| Tag shape | **`share:<slug>`** | Single namespace, slug is already opaque + 72-bit entropy. No collision risk. |
| Revalidation trigger | **Backend → frontend webhook** | Backend share toggle is the source of truth. After every `set_share_slug` / `revoke_share_slug`, it POSTs to a small frontend route that calls `revalidateTag`. |
| Webhook auth | **Shared secret in header** | New env var `REVALIDATE_SECRET`; constant-time compare on the frontend side. Reuses the same pattern as v0.8.1's `CRON_SECRET`. |
| Webhook contract | **`POST /api/revalidate` with `{tag: "share:<slug>"}` JSON body** | Single endpoint, single body shape. Frontend validates the tag prefix to avoid being a generic revalidation gadget. |
| Failure mode | **Fire-and-forget with timeout** | Backend never blocks the share toggle on the webhook. Failed revalidations get logged + Sentry-tagged but the toggle itself returns 200/204 to the user. The next natural revalidation (next deploy, fallback TTL) closes the gap. |
| Fallback TTL | **`cacheLife({ revalidate: 3600 })`** | One-hour safety net so a missed webhook isn't unbounded staleness. Anything that gets revoked + webhook-missed still flips within an hour. |
| Cache miss on 404 | **Do not cache 404** | If `loadShared` raises `notFound()` we want the *next* request to retry against the backend (the slug might have been re-shared). Cache only successful payloads. |
| OG image route | **Also cached, same tag** | `/share/[slug]/opengraph-image.tsx` shares the slug → same `share:<slug>` tag so social previews invalidate alongside the page. |

## 3. Operating context

At ~100 users/day, share-page traffic is bursty (a viral share hits hard during the burst, drops to zero after). ISR makes burst-time hits sub-100ms; revocation is rare but must be instant when it happens (legal / privacy / "I changed my mind" cases). This slice optimises the burst case without compromising the rare-revocation case.

## 4. Architecture (one paragraph)

A new `revalidateShareSlug(slug)` helper in `app/share/webhook.py` issues a fire-and-forget `POST` to `{FRONTEND_BASE_URL}/api/revalidate` with `{"tag": f"share:{slug}"}` and a `X-Revalidate-Secret` header. `set_share_slug` and `revoke_share_slug` call it as a `BackgroundTasks` task so the HTTP response to the user returns immediately. The frontend gains a new route `frontend/src/app/api/revalidate/route.ts` that validates the secret via `crypto.timingSafeEqual`, validates the tag matches `^share:[A-Za-z0-9_-]{1,64}$`, calls `revalidateTag(tag)`, and returns `204`. The existing `frontend/src/app/share/[slug]/page.tsx` switches to a cached server-async-function pattern: `loadShared(slug)` becomes `'use cache'`, calls `cacheTag(\`share:${slug}\`)` + `cacheLife({ revalidate: 3600 })`, and `force-dynamic` comes off the page. The OG image route at `/share/[slug]/opengraph-image.tsx` gets the same `'use cache'` treatment with the same tag.

## 6. Data flow

### 6.1 Read (happy path)

1. Visitor hits `https://<host>/share/abc123def456`.
2. Next.js evaluates `page.tsx`. The cached `loadShared("abc123def456")` is a hit → cached JSON returned in <50ms.
3. Page renders the existing `<ShareAttribution>` + `<ResultsView>` against the cached data.
4. No backend call. Cache TTL 3600s.

### 6.2 Read (cold or post-revalidation)

1. Visitor hits the URL; `loadShared` cache misses.
2. Function executes: fetches `${NEXT_PUBLIC_BACKEND_URL}/share/abc123def456`.
3. Backend `share.get_shared` returns the JSON.
4. Frontend caches the result under tag `share:abc123def456`. Returns to renderer.

### 6.3 Share toggle (POST)

1. Signed-in owner clicks "Share" on `/u/{username}`.
2. Frontend POSTs `/analyses/{id}/share` with session cookie.
3. Backend `share_analysis` → `set_share_slug` → `slug = "newslugXYZ"`. `db.commit()`.
4. `BackgroundTasks.add_task(revalidate_share_slug, "newslugXYZ")`.
5. Backend returns `{share_slug, share_url}` to the frontend.
6. Background task POSTs `${FRONTEND_BASE_URL}/api/revalidate` with `{tag: "share:newslugXYZ"}` + `X-Revalidate-Secret`. Frontend route invokes `revalidateTag("share:newslugXYZ")` and returns 204.
7. Next request for the new slug cache-misses → fetches → caches. (For a brand-new slug there's no prior cache to bust, but the call is idempotent and cheap.)

### 6.4 Revoke (DELETE)

1. Owner clicks "Stop sharing".
2. Frontend DELETEs `/analyses/{id}/share`.
3. Backend `revoke_share` → `revoke_share_slug` returns `removed_slug = "oldSlug123"`. `db.commit()`.
4. `BackgroundTasks.add_task(revalidate_share_slug, "oldSlug123")`.
5. Backend returns 204.
6. Background task hits `/api/revalidate` with `{tag: "share:oldSlug123"}`. Frontend invalidates.
7. **Next request for `/share/oldSlug123` cache-misses → backend `share.get_shared` returns 404 → page calls `notFound()` → 404 rendered.** The 404 path is not cached, so retries against the backend each time. If the analysis is ever re-shared with that exact slug (which won't happen — `_new_slug()` is 72-bit random), it'd just cache the fresh response.

## 7. Error contract

| Source | Code | Body | When |
| --- | --- | --- | --- |
| Frontend `/api/revalidate` | 401 | `{"error": "invalid_secret"}` | Missing or wrong `X-Revalidate-Secret`. |
| Frontend `/api/revalidate` | 400 | `{"error": "bad_tag"}` | Body missing `tag`, tag not a string, or tag doesn't match `^share:[A-Za-z0-9_-]{1,64}$`. |
| Frontend `/api/revalidate` | 204 | empty | Valid request; tag invalidated. |
| Backend webhook helper | always no-op | n/a | All failures swallowed + logged; the caller never sees them. |
| Backend share toggle | 200/204 | unchanged | Webhook failure does NOT affect the toggle's HTTP response. |

## 8. Configuration

Two new env vars. Both are required on Vercel Production + Preview for the feature to fire; absence makes the webhook a logged no-op (graceful degradation — share toggles still work, ISR just stays cached until natural revalidation).

| Var | Where set | Format | Provisioning |
| --- | --- | --- | --- |
| `FRONTEND_BASE_URL` | Backend env | `https://skill-issue-tau.vercel.app` (no trailing slash) | Hard-code in Vercel env per environment. |
| `REVALIDATE_SECRET` | **Both** frontend and backend | 64 hex chars | `python -c "import secrets; print(secrets.token_hex(32))"`. Same value on both sides. Mark "Sensitive" on Vercel. |

## 9. Security considerations

- **`REVALIDATE_SECRET` is a shared secret.** A leak lets anyone invalidate any share-tag, which is an annoyance (cache thrash) not a privacy breach — the 404 contract is unchanged either way. Severity: low. Mitigation: standard Vercel "Sensitive" env, no-log discipline.
- **Tag regex `^share:[A-Za-z0-9_-]{1,64}$`** prevents the route from being a generic revalidation gadget. Even if the secret leaks, an attacker can't `revalidateTag("*")` or invalidate anything outside the share namespace.
- **Constant-time compare via `crypto.timingSafeEqual`** on the Next.js side (same pattern as `hmac.compare_digest` on the backend's cron route).
- **No CORS allow-list on `/api/revalidate`** — it's a server-to-server endpoint, not browser-facing. CORS isn't relevant; the secret is the only auth.
- **Body size limit** — implicit via Next.js defaults (~4MB). Body shape is two fields; no risk of huge-body DoS at platform scale.

## 10. Test strategy

Backend (5 unit tests in `tests/share/test_webhook.py`):

1. **No-op when unconfigured.** Both env vars unset → `revalidate_share_slug("x")` logs a warning and returns. Asserts no HTTP call.
2. **Happy path.** Both env vars set → captures the outgoing request via `respx`. Asserts URL == `{FRONTEND_BASE_URL}/api/revalidate`, header `X-Revalidate-Secret` == secret, body `{"tag": "share:x"}`.
3. **4xx response is logged + swallowed.** Backend responds 401 to the webhook → function does NOT raise. Sentry breadcrumb captured.
4. **Timeout is logged + swallowed.** Mock a 6s delay → function returns within 5s timeout, does NOT raise.
5. **Tag prefix is always `share:`.** No matter what the caller passes for `slug`, the outgoing tag is `share:<slug>`. Guards against future callers passing a raw tag.

Backend (extend `tests/routers/test_analyses_share.py`, 2 new tests):

6. **Share POST schedules revalidation.** `FastAPI.BackgroundTasks` is patched; `share_analysis` is called → assert `add_task(revalidate_share_slug, "<expected_slug>")` was invoked.
7. **Revoke DELETE schedules revalidation with the just-removed slug.** Same shape against `revoke_share_slug`'s return.

Frontend (5 vitest cases in `frontend/src/app/api/revalidate/__tests__/route.test.ts`):

8. **401 on missing secret.** No header → 401 `{"error": "invalid_secret"}`.
9. **401 on wrong secret.** Wrong value → 401 (same body) — constant-time compare.
10. **400 on missing/malformed tag.** Empty body / non-string tag → 400 `{"error": "bad_tag"}`.
11. **400 on bad tag format.** `tag: "garbage"` (no `share:` prefix) → 400.
12. **204 + `revalidateTag` called.** Valid request → mocked `revalidateTag` invoked with `"share:abc123"`, response 204.

Integration smoke (manual post-deploy):

13. Share an analysis → verify the new slug renders fast (cache hit on second visit). Revoke → verify the slug 404s on the next request, not after a TTL.

## 13. Out of scope

- **Revalidating `/u/[username]` after force-refresh.** That route is `cache: "no-store"` today and the v0.8.2 force-refresh button already triggers a backend re-ingest; there's no frontend cache to bust.
- **Stale-while-revalidate / SWR semantics.** `cacheLife({ revalidate: 3600 })` is a hard fallback only; we don't want stale-while-revalidate on a privacy-sensitive route.
- **Sentry alert rules for repeated webhook failures.** Deferred to the v0.8.x patch that wires alert rules globally.
- **Webhook batching / debouncing.** A user toggling share-state in rapid succession would issue multiple webhook calls; at 100 users/day this is fine. Revisit if it ever matters.
- **`Vercel Routing Middleware` for share-slug auth.** Tags solve the same problem with less complexity; only worth revisiting if we need per-region edge cache invalidation, which we don't.
