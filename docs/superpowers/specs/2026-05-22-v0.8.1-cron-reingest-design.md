# v0.8.1 — Cron daily re-ingestion design spec

**Status:** Designed. Implementation plan to follow under `docs/superpowers/plans/`.
**Date:** 2026-05-22.
**Author:** Claude (Opus 4.7) with Shaan.

---

## 1. Goal

A signed-in user who returns the next day sees fresh scores on every analysis they previously saved, without paying the cold-ingest cost on their first visit. The mechanism is a once-nightly Vercel Cron that hits a new authenticated backend route, re-ingests the oldest-stale saved analyses up to a chunk cap, and writes the result back through the v0.7.0 Layer A cache so concurrent reads benefit too. Sentry (shipped in v0.8.0) makes silent failures impossible — every chunk emits structured logs and surfaces fatal errors as captured events.

Nothing else lands in this slice. Force-refresh button (v0.8.2), share-page revalidation (v0.8.3), and the `vercel.json → vercel.ts` migration (v0.8.4) each earn their own patch release.

## 2. Locked scope decisions (2026-05-22)

| Decision | Choice | Why |
| --- | --- | --- |
| Refresh target | **All saved `analyses` rows** | Simplest mental model — every persisted analysis stays current. Volume scales linearly with usage; chunk cap handles overflow. |
| Token strategy | **Owner's latest unexpired session token, falling back to `GITHUB_TOKEN`** | Scales infinitely with user count (each user contributes their own 5000/hr quota). v0.5.0 already stores encrypted tokens on `sessions`; we reuse that primitive, no new storage. App token covers the no-active-session case. |
| Chunking | **Simple cap, spill to tomorrow** | Process up to N=25 oldest-stale analyses per fire; if the wall-clock cap is hit first, commit what's done and exit. No self-invocation, no resume tokens, no continuation logic. YAGNI until growth forces otherwise. |
| Wall-clock cap | **240s** (60s safety margin under Vercel's 300s function timeout) | Each refresh runs the existing `get_report_for_user` pipeline — typically 5-10s warm, occasionally 20-30s cold. 240s lets us safely commit progress and return before Vercel terminates. |
| Cache strategy | **Write-through via existing `get_report_for_user`** | Layer A Redis cache is keyed by lowercased `target_login`. When user X's save of `octocat` refreshes, the cache key warms for every other user's save of `octocat` too — N:1 GH-call savings come for free with no special code. |
| Narrative pre-warming | **Never** | New scores_hash invalidates the existing (user, scores_hash, mode) narrative-cache key naturally. Pre-warming would burn LLM budget against an uncertain "user will return tomorrow AND look at narrative" prior. Next request misses cache, regenerates fresh. |
| Schedule | **`0 3 * * *`** (03:00 UTC) | Low-traffic window for our likely user base (NA/EU). Aligns with the v0.7.0 GitHub-API cache TTLs (15min-1h) — yesterday's Layer C entries have aged out, so refresh ingests genuinely-new data. |
| Auth | **`Authorization: Bearer ${CRON_SECRET}`** header | Vercel Cron's standard pattern. Missing/wrong → 401, no further side effects. |
| Cron-entry location | **`vercel.json`** (current location) | v0.8.4 migrates the entire project to `vercel.ts`; cron entry comes along then. Not worth pulling that work forward. |
| Failure handling | **Per-row isolation; rate-limit cliff stops the chunk** | One bad analysis (404, schema drift) → Sentry breadcrumb + skip + continue. 403 rate-limit cliff → stop the chunk (continuing burns more 403s), Sentry capture, return 207. DB error → bubble + Sentry capture. |
| Out of slice | Force-refresh button (v0.8.2), share-page `revalidateTag` (v0.8.3), `vercel.ts` migration (v0.8.4), persistent dedup of "same-target saved by N users" (v0.9.x) | Each is independent; bundled = slower delivery. |

## 3. Architecture (one paragraph)

A single `crons` entry in `vercel.json` fires `POST /_/backend/cron/refresh-saved-analyses` every day at 03:00 UTC. The route — declared on a new `app/routers/cron.py` — verifies `Authorization: Bearer ${CRON_SECRET}`, then asks `app/persistence/refresh.py::iter_stale_analyses(session, limit=25)` for the N oldest analyses whose latest run's `ingestion_completed_at` is older than 24h (or whose run set is empty). For each row, `app/cron/refresh.py::refresh_one(session, analysis)` resolves a GitHub token via `resolve_token_for_analysis` (latest unexpired `sessions` row for the owner → decrypt → fall back to `Settings.github_token`), invokes the existing `get_report_for_user(target_login, token=...)` pipeline (which write-throughs the Layer A cache), and records a new `analysis_runs` row plus updates `analyses.latest_run_id`. The route is wrapped in a 240s deadline guard: each iteration checks remaining budget and exits cleanly if exhausted. Per-row exceptions never propagate — each is caught, logged with structlog + Sentry breadcrumb, and counted toward the response summary. A 403 rate-limit cliff is the one case that stops the chunk (continuing would burn more 403s) and is reported as a Sentry capture. The response is JSON: `{processed, succeeded, skipped, rate_limited, deadline_reached, errors[]}`.

## 5. Data flow

1. Vercel Cron fires `POST /_/backend/cron/refresh-saved-analyses` at 03:00 UTC with header `Authorization: Bearer ${CRON_SECRET}`.
2. `require_cron_auth` dependency verifies the bearer; mismatch returns 401 and no work happens.
3. Handler opens a single async DB session, calls `iter_stale_analyses(session, limit=25)`.
4. For each analysis in the returned list:
   a. `resolve_token_for_analysis(session, analysis)` → `(token, source)`. Source is logged but doesn't change downstream behavior.
   b. Build a request-scoped `GitHubClient(token=token)`.
   c. Call `get_report_for_user(target_login, github_client=...)` — this is the same path `/analyze/{username}` uses. Layer A Redis cache is written through on success.
   d. `record_run_for_analysis(session, analysis, report)` — inserts new `analysis_runs` row, sets `analyses.latest_run_id`, bumps `analyses.updated_at`.
   e. Append to summary: `{analysis_id, target_login, owner_user_id, token_source, status: "succeeded", duration_ms}`.
5. Between iterations, check remaining wall-clock budget. If exhausted, set `deadline_reached=true` and break.
6. Commit the DB session.
7. Return JSON summary.

## 6. Error budget + Sentry contract

| Event | What raises it | Severity | Sentry action |
| --- | --- | --- | --- |
| `analysis_id=X target=Y refresh_started` | Per iteration | info | breadcrumb |
| `analysis_id=X target=Y refresh_succeeded duration_ms=N` | Per success | info | breadcrumb |
| `analysis_id=X target=Y not_found` | GH 404 on target user (account deleted) | warn | breadcrumb, skip, continue |
| `analysis_id=X target=Y org_detected` | Target is now an org (was a user before — extremely rare) | warn | breadcrumb, skip, continue |
| `analysis_id=X target=Y unexpected_error` | Anything else from `get_report_for_user` | error | breadcrumb + Sentry capture, skip, continue |
| `cron rate_limit_cliff after N analyses` | GH 403 with rate-limit headers | error | Sentry capture, stop chunk, return 207 |
| `cron db_error` | SQLAlchemy `OperationalError` etc. | error | Sentry capture, raise (Vercel logs the 500) |

The PII contract from v0.8.0 carries forward: no `access_token`, no `access_token_ct`, no encrypted session bytes, no `Authorization` header values ever in event bodies. The existing `scrub_event` hook covers all of these.

## 7. Test strategy

Cron code is pure orchestration over already-tested pieces (`get_report_for_user`, `record_run`, `resolve_token`). The new tests focus on:

1. **Authentication boundary.** Wrong bearer / missing bearer → 401. Correct bearer reaches the handler.
2. **Token resolver.** Active session present → user_session source. Expired session present → app_fallback. No session at all → app_fallback. Token decryption matches what was stored.
3. **Query ordering.** Analyses with no runs sort first. Among rows with runs, oldest `ingestion_completed_at` first. Rows refreshed within 24h excluded.
4. **Per-row isolation.** Injecting a `RuntimeError` on iteration 3 of 5 → iteration 3 reported as `unexpected_error`, iterations 4-5 still process.
5. **Deadline guard.** With a fake clock advancing 50s per iteration and `deadline_seconds=240`, iterations 1-4 process, iteration 5 hits the deadline and sets `deadline_reached=true`.
6. **Rate-limit cliff.** Injecting an httpx response with status 403 + `X-RateLimit-Remaining: 0` on iteration 2 → chunk stops at iteration 2, summary records `rate_limited=1`, Sentry capture asserted.
7. **Cache write-through (integration).** After `run_refresh_chunk` succeeds for `octocat`, a subsequent `get_report_for_user("octocat")` call returns the cached report without triggering `_live_ingest` — reuses the v0.7.0 assertion pattern from `tests/test_report_cache.py::test_second_call_hits_cache_not_live_ingest`.
8. **Idempotency.** Running the chunk twice in a row produces zero work on the second run (everything is within 24h).

DB-fixture tests gated on `TEST_DATABASE_URL` (same gate as v0.5.0). FakeRedis fixture covers the cache write-through assertion. `respx` mocks GH 403 + 404 paths.

- [ ] `POST /cron/refresh-saved-analyses` with correct bearer + `TEST_DATABASE_URL` set → 200, summary JSON shape matches §5.7.
- [ ] One bad analysis (404 / RuntimeError) doesn't block subsequent rows.
- [ ] A new `analysis_runs` row appears for each successfully-refreshed analysis.
- [ ] Layer A Redis cache is populated for each refreshed target (FakeRedis test).
- [ ] Wall-clock cap honored — fake clock test passes.

## 9. Provisioning gate (user action)

Before the slice can ship to prod, the user provisions:

1. **`CRON_SECRET`** — a random 32+ byte string (`openssl rand -hex 32`), pasted into Vercel Production + Preview as a sensitive env var.
2. **Vercel Cron enabled on the project** — confirm Hobby tier supports a single daily cron entry (the project is on Hobby per v0.8.0's "free-free" constraint). If Hobby caps differ, surface that during implementation and propose either upgrading or adjusting the cron schedule.

Both are AGENTS.md rule 5 items — Claude does not provision these without explicit user action.

## 10. Out of scope

- **Force refresh button** — v0.8.2 ships `DELETE /me/cache/{username}` + the UI affordance.
- **`revalidateTag` for `/share/[slug]`** — v0.8.3 ships the backend↔frontend webhook + the ISR enablement.
- **`vercel.json → vercel.ts`** — v0.8.4 ships the migration; the cron entry moves with it.
- **Pre-warming narratives** — never. Designed-out per §2.
- **Persistent dedup of "same target saved by N users"** — Layer A cache handles GH-side cost today. Persistent dedup would change the `analyses ↔ analysis_runs` shape; defer to v0.9.x where the persistence layer gets a hardening pass anyway.
- **Recursive self-invocation** — designed out per §2. Re-open if simple-cap-spill-to-tomorrow falls behind (signal: `deadline_reached=true` on consecutive nights with growing backlog).
- **Sentry alert rules** — deferred to a future v0.8.x patch per v0.8.0's stated plan.
