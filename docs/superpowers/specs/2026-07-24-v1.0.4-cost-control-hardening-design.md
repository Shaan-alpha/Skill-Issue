# v1.0.4 — Cost-control fairness & security hardening — Design

> **Status:** draft 2026-07-24, awaiting user review before `writing-plans`.
> **Slice family:** v1.0.x post-launch hardening.
> **Origin:** the 2026-07-24 full security audit (37 findings). This slice takes the audit's **Batch 1 + the lower-risk half of Batch 2**. The heavy ingest-path changes (SI-03, SI-06, SI-07, SI-08, SI-09) are split into a follow-up slice **v1.0.5 — Ingest amplification containment**, so the hottest code gets its own review/verify cycle.
> **Revisits:** two decisions made in `2026-05-27-v0.9.2-rate-limiting-design.md` (fail-open on cache absence; trusting `x-real-ip` / leftmost `x-forwarded-for`).

## 1. Goal

Close the audit's cost & availability gaps that are cheap and low-risk, plus the config/CI/observability quick wins. No user-facing feature changes. Three outcomes:

1. **Fairness** — no single anonymous IP can drain the global LLM budget and degrade AI for everyone (SI-02).
2. **Fail-closed cost controls** — a Redis outage no longer removes rate limiting and the LLM budget simultaneously (SI-01), and a forgotten proxy secret no longer disables anonymous `/analyze` limiting entirely (SI-05). Client-IP derivation stops trusting a spoofable header (SI-04).
3. **Hardening quick wins** — the internal proxy secret can no longer leak to Sentry (SI-11); CI runs least-privilege (SI-12); `.env.example` stops shipping an insecure cookie default (SI-13); a session-decrypt failure degrades to re-login instead of a 500 (SI-22).

## 3. Background — what we are revisiting

The v0.9.2 rate-limiting design deliberately chose **fail-open** ("the cache is a perf/abuse-mitigation layer, never a correctness boundary") and derived the client IP from `x-real-ip` then leftmost `x-forwarded-for`. Two things changed the calculus:

1. **The LLM budget is real money** and is a single global counter. Fail-open there means uncapped OpenAI/Groq spend during a Redis blip — a cost boundary, not just an abuse one.
2. **Vercel's platform guarantee is specific.** Per [Vercel request-headers docs](https://vercel.com/docs/headers/request-headers): Vercel **overwrites `x-forwarded-for`** and does not forward external IPs, *to prevent spoofing*. It makes **no such guarantee for `x-real-ip`** — which the current `client_ip()` trusts *first*. So the spoof-proof source is `x-forwarded-for` (or `x-vercel-forwarded-for`, identical but preserved behind an upstream proxy), and trusting `x-real-ip` ahead of it is the fragile part.

This slice tightens those two calls for the cost-sensitive paths while keeping the fail-open ergonomics where they are genuinely just perf (e.g. the Report cache and singleflight remain fail-open — a cache miss is correct-but-slow, never a spend or security event).

## 4. Workstream A — Rate-limit & budget correctness

### 4.1 SI-02 — Per-subject LLM budget

**Problem.** `narrative_daily_limit` (default 50) is a single global key `narrative:<date>`. `narrative_anon_per_ip_per_hour` is 30, so one IP can spend the whole global budget in <2h; every user then silently gets `fallback_narrative`.

**Model — global ceiling + per-subject daily caps.** A narrative consumes a real LLM call only if **both** the global budget **and** the caller's per-subject budget have headroom. Otherwise it serves the existing fallback (no spend). New `Settings` fields (all env-overridable):

| Setting | Env var | Default | Meaning |
| --- | --- | --- | --- |
| `narrative_daily_limit` | `NARRATIVE_DAILY_LIMIT` | **500** (was 50) | Global hard $ ceiling / UTC-day |
| `narrative_anon_ip_daily_limit` | `NARRATIVE_ANON_IP_DAILY_LIMIT` | 10 | Per anonymous IP / UTC-day |
| `narrative_user_daily_limit` | `NARRATIVE_USER_DAILY_LIMIT` | 40 | Per signed-in user / UTC-day |

**Subject derivation is shared with the rate limiter.** Extract a helper in `app/ratelimit.py`:

```python
def resolve_budget_subject(request, session) -> tuple[str, int]:
    """Return (subject_key, per_subject_daily_limit) matching the rate-limiter's
    user:/ip: scheme. Signed-in → ("user:<id>", user_daily). Anon → ("ip:<addr>", anon_daily)."""
```

`get_narrative` (router) resolves it from `request` + `optional_session` and threads it into the service.

**Consume semantics (reserve-then-release).** `DailyBudget` gains subject awareness:

```python
async def atry_consume(self, *, subject: str | None = None, subject_limit: int | None = None) -> bool
```

Redis path, keys `narrative:<date>` (global) and `narrative:<subject>:<date>` (per-subject), both `EXPIRE` ~2 days:
1. If `subject` given: `INCR` subject key. If result > `subject_limit` → `DECR` subject key, return `False` (subject exhausted → fallback).
2. `INCR` global key. If result > global limit → `DECR` global (and `DECR` subject if it was incremented) → return `False`.
3. Return `True`.

The conditional `DECR` on rejection keeps counters from drifting when one dimension blocks the other (and avoids penalizing a subject for a request that never spent). Concurrency can overshoot a limit by at most the in-flight count — acceptable for a best-effort cost ceiling, consistent with the existing INCR-and-compare primitive. `subject=None` preserves today's global-only behavior for existing callers/tests.

**Relationship to the existing per-hour narrative rate limit.** These are complementary, not redundant: `narrative_anon_per_ip_per_hour` (30/hr, from v0.9.2) caps *request volume* — DB writes and compute — and stays unchanged. The new per-day budget caps *LLM spend*. It is intentionally the stricter of the two: once an anonymous IP has consumed its 10 real narratives for the day, further requests are served the fallback (page still loads, no spend), while the hourly limiter continues to protect compute. Signed-in users get the more generous 40/day. All three knobs are env-tunable if the anon/day figure proves too tight for real traffic.

**Service wiring.** `NarrativeService.stream_narrative(mode, report, *, meta, subject=None, subject_limit=None)` forwards both to `budget.atry_consume(...)`. The fallback branch (`service.py:70`) is unchanged in shape.

> Note: refunding the budget slot on a mid-stream client abort is **SI-07**, deferred to v1.0.5. This slice only adds the second budget dimension.

### 4.2 SI-04 — Trust Vercel's spoof-proof forwarded header

**Change `client_ip()` (`app/ratelimit.py`).** New resolution order:
1. Trusted `x-client-ip` — **only** when `is_trusted_proxy(request)` (unchanged; the first-party RSC override).
2. Leftmost hop of the configured trusted forwarded header (default `x-forwarded-for`, which Vercel overwrites at the edge and does not forward external copies of). New setting `trusted_client_ip_header` (env `TRUSTED_CLIENT_IP_HEADER`, default `"x-forwarded-for"`) so a non-Vercel deploy or an upstream-proxy setup can point it at `x-vercel-forwarded-for` without a code change.
3. `request.client.host`.
4. `"unknown"`.

**Removed:** the `x-real-ip` branch (not a documented spoof-proof header on Vercel). A comment cites the Vercel guarantee so the reliance is explicit in-code (the thing v0.9.2 left implicit).

**Why leftmost is safe here:** Vercel *replaces* `x-forwarded-for` with the true client chain rather than appending an attacker's value, so the leftmost entry is the real client for a direct request. The `x-client-ip`+secret path still overrides it for RSC-proxied `/analyze`.

### 4.3 SI-05 — Anonymous `/analyze` fails closed when the proxy secret is unset

**Problem.** When `internal_proxy_secret` is `None`, `make_rate_limiter(via_trusted_proxy=True)` **skips anon enforcement entirely** — so a deploy that forgets the (optional) secret ships zero anonymous `/analyze` limiting, and a direct-to-backend attacker is unmetered.

**Constraint.** We can't just fall back to strict per-IP limiting in this mode: anon `/analyze` proxied through the Next RSC arrives from a Vercel-infra egress IP, so strict per-IP would collapse all website visitors into one bucket and throttle them collectively (the exact reason v0.9.2 chose to skip).

**Fix — conservative global backstop, not skip.** When the secret is unset, enforce the anon analyze cap against a single shared subject `ip:unattributed` at a higher configurable limit:

| Setting | Env var | Default |
| --- | --- | --- |
| `analyze_unattributed_per_hour` | `ANALYZE_UNATTRIBUTED_PER_HOUR` | 300 |

This caps total anonymous `/analyze` volume (bounding the direct-attacker DoS) without throttling individual visitors at the strict 20/hr. Production (skillissue.tech) already sets `INTERNAL_PROXY_SECRET` (provisioned in v0.9.2), so this backstop is a safety net for misconfigured/forked deploys, not the normal path. The existing loud warning log is kept and re-labelled `event=rate_limit.unattributed_backstop`. **Trade-off, stated:** once the backstop bucket fills, anonymous analyze is collectively throttled until the next hour — strictly better than unlimited, and only reachable in the secret-unset mode.

## 5. Workstream B — Fail-closed cost controls (SI-01)

**Problem.** Three fail-open points collapse together when Redis is `None` or erroring: `make_rate_limiter` returns early (no limiting); `try_increment_counter` returns `allowed=True` on error; `DailyBudget.atry_consume` allows on error. A single Upstash incident removes rate limiting **and** the LLM spend cap at once.

**Fix — in-process conservative fallback.** New module `app/ratelimit_fallback.py`: a per-process, lock-guarded counter map keyed on `(subject, bucket)` with automatic pruning of stale buckets, plus an equivalent per-process daily budget counter.

- **Rate limiter:** when `get_cache()` is `None`, or when `try_increment_counter` reports the Redis-error sentinel, consult the in-process limiter using the *same* limit fields instead of allowing unconditionally.
- **Budget:** `DailyBudget` already has an in-process `try_consume` fallback for the unconfigured case; extend it so a Redis **error** (not just unset) also routes to the in-process counter rather than failing open.
- **Signal:** emit `event=rate_limit.degraded_local` (warn) the first time per process the fallback path is taken, so the degraded state is visible in logs/Sentry.

**Known limitation (documented, not fixed here):** the in-process fallback is per-instance, so on horizontally-scaled Fluid Compute the effective ceiling is `limit × instances` (audit SI-10). That is strictly better than unlimited and acceptable as a degraded-mode backstop; the per-instance division is a backlog item, noted in `OBSERVABILITY.md`.

**Unchanged (still fail-open by design):** the Report cache and singleflight lock — a miss there is correct-but-slower, never a spend or security event.

## 6. Workstream D — Config & CI hardening quick wins

### 6.1 SI-11 — Sentry header scrub
- Backend `app/observability/sentry.py`: add `x-internal-secret`, `x-revalidate-secret`, `x-client-ip`, `x-forwarded-for`, `x-real-ip` to `_SCRUB_HEADER_NAMES`. (The last two also address the IP-PII half of audit SI-32.)
- Frontend `src/observability/scrub.ts`: mirror the same additions into `SCRUB_HEADER_NAMES` (the file's contract requires the two lists stay in sync).
- The scrub already lowercases header names, so no casing issue on this path.

### 6.2 SI-12 — CI least privilege
- `.github/workflows/ci.yml`: add workflow-level `permissions: { contents: read }`. No job needs more (release.yml keeps its own `contents: write`).

### 6.3 SI-13 — `.env.example` cookie default
- Comment the active line to `# COOKIE_SECURE=false  # local HTTP dev only` so `cp .env.example .env` no longer overrides the fail-closed `cookie_secure=True` default.

### 6.4 SI-22 — Graceful session-decrypt failure
- `auth/sessions.py::get_session_with_token`: wrap the `decrypt_access_token` call in `try/except InvalidEncKey`; on failure return `None` (treated as an invalid session → clean re-login) and log `event=session.decrypt_failed` (no ciphertext/token in the log). This makes `SESSION_TOKEN_ENC_KEY` rotation a graceful mass-logout instead of a mass-500 across every endpoint that depends on `optional_session`.

## 12. Exit criteria

- [ ] One anonymous IP over `narrative_anon_ip_daily_limit` → fallback narrative, while a *different* IP/user under its cap still gets a real narrative (global not yet exhausted). Global over `narrative_daily_limit` → everyone gets fallback.
- [ ] Reserve-then-release: a request blocked by the global cap does not permanently consume the subject's counter (verified by counter state after a blocked call).
- [ ] `client_ip()` ignores `x-real-ip`; a forged `X-Real-IP` no longer changes the rate-limit subject; trusted `x-client-ip` (valid secret) and leftmost `x-forwarded-for` still resolve correctly.
- [ ] Secret unset → anon `/analyze` limited via the `ip:unattributed` backstop (429 over `analyze_unattributed_per_hour`), never unlimited; secret set → unchanged per-IP behavior.
- [ ] Cache `None` and Redis error both enforce the in-process fallback limiter and budget (not fail-open); `degraded_local` logged once per process.
- [ ] A Sentry event carrying `x-internal-secret` / `x-revalidate-secret` / IP headers is emitted scrubbed (backend + frontend tests green).
- [ ] A session row with corrupt ciphertext → `get_session_with_token` returns `None`; no 500; key rotation is a graceful mass-logout.
