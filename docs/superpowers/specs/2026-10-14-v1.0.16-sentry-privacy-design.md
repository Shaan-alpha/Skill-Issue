# v1.0.16 — Privacy patch: Sentry and PostHog (design)

**Date:** 2026-10-14 · **Status:** design approved section by section in brainstorming (2026-10-14), then revised after a two-agent fact and risk review; this written spec awaits the operator's review · **Slice type:** patch (privacy and hygiene)

## 1. Why

Research for the toolchain majors (four read-only researchers and a critic, 2026-10-14), then a fact-checker and a risk critic on this spec's first draft, found that the PII contract in [`docs/OBSERVABILITY.md`](../../OBSERVABILITY.md) does not hold on the SDKs running today. The privacy page does not hold either. Raw session ids must never reach Sentry, and the privacy page says a visitor's IP is "used transiently".

### 1.1 Frontend (`@sentry/nextjs` 10.76.2)

- **Cookies.** With `sendDefaultPii: false`, cookies resolve to a deny list rather than `false` (`@sentry/core` `defaultPiiToCollectionOptions.js`). So the RequestData integration attaches every cookie, parsed raw, as `event.request.cookies`; its event path applies no list (`requestdata.js`). That includes `si_session`, which the backend sets on the shared origin with path `/`. `onRequestError` errors get it through `captureRequestError`. `scrubEvent` removes the `cookie` header but not `request.cookies`.
- **Transactions are never scrubbed.**
  - The Node HTTP server subscription stores each incoming request on the isolation scope (`server-subscription.js`), and the Next.js init keeps that subscription. So RequestData adds the request to every event, including the 10% sampled as transactions.
  - `beforeSend` runs on errors only, so transactions keep the raw `cookie` header and `request.cookies` too.
  - The SDK also copies request headers onto every server root span as `http.request.header.*` attributes, one per cookie included (`handleOnSpanStart.js`, `addHeadersAsAttributes.js`), and these land in `contexts.trace.data`.
- **Query strings in other fields.** Next puts the raw `req.url` into the root span's `http.target` and into `onRequestError`'s `path`, which Sentry stores as `contexts.nextjs.request_path`. Neither field is filtered.
- **Bodies.** The server captures incoming request bodies up to "medium" (`maxRequestBodySize` defaults to `medium`), whatever `httpBodies` says.
- **Vercel's headers.** `x-vercel-ip-city`, `-latitude`, `-longitude`, `-postal-code` and the rest of the `x-vercel-ip-*` family, `x-vercel-oidc-token` (a project JWT), `x-vercel-id`, and `x-revalidate-secret` on the backend's revalidate calls all pass through. Only the SDK's 12 IP header names are stripped, because `userInfo` is false.
- **Frame variables:** none. The Node SDK attaches locals only with `includeLocalVariables`, which is unset.

### 1.2 Backend (sentry-python 2.72)

- **Headers.** sentry-python filters seven headers itself (`_wsgi_common.py` `SENSITIVE_HEADERS`), and `scrub_event` removes a few more, on errors only. Transactions keep `x-internal-secret` (sent by the frontend server on every `/analyze` call), `x-vercel-forwarded-for` (the visitor IP), the `x-vercel-ip-*` family, `x-vercel-oidc-token` and `x-vercel-id`.
- **Frame variables carry everything.** `include_local_variables` defaults to true, and the SDK serializes the locals of every frame, framework frames included. Starlette's `Request` and the raw ASGI `scope` serialize as dicts whose `headers` are lists of byte pairs. So the visitor's cookies, `x-internal-secret` and `Authorization: Bearer <CRON_SECRET>` sit in list elements, where no name-based rule can find them. The locals also include:
  - `access_token` in `_live_ingest`: a user's GitHub OAuth token, or the app's `GITHUB_TOKEN`;
  - `resolved` in `optional_session`: the decrypted token;
  - `session_id` and `key` (the AES key) in `get_session_with_token`;
  - `subject = "ip:<visitor IP>"` in the narrator;
  - httpcore frames holding raw `Authorization` headers.

  The SDK's EventScrubber matches exact names only (`token`, `session`, … but not `access_token`, `session_id` or `key`).
- **Query strings and bodies.** Events keep the query string, which includes OAuth `code` and `state` on callback errors. Request bodies are captured up to "medium".
- **SQL parameters.** The engine doesn't set `hide_parameters`, so a database error message can include bound parameters, such as an email.

### 1.3 PostHog

PostHog sends no cookies, tokens or secrets: `si_session` is httpOnly, and identify sends only the database user id. But by default PostHog stores each visitor's IP and enriches it with GeoIP, which contradicts the privacy page. The PostHog cookie is missing from the privacy page's cookie list. Session recording is left to the project setting, with text unmasked by default.

### 1.4 What is known to have reached Sentry (checked 2026-10-14)

Only issue lists were read, so no stored value entered a transcript. Error events are kept for 90 days.
- **Frontend:** 4 issues in that window, all browser-side, where the SDK sends no IP and no cookies.
- **Backend:** 3 issues, BACKEND-4, -5 and -6 (21 events on `/analyze` and `/narrative`, July and August). With locals on, their frames very probably hold the request headers and an `access_token`. Any `si_session` in them has expired (30-day sessions); app secrets and OAuth tokens have not.
- **Transactions:** not inspected.
  - Frontend transactions very probably stored `si_session` for signed-in visitors. The `session` snippet filters the span attribute copy, but not `request.cookies`.
  - Backend transactions stored the internal secret, unless Relay's default key rules caught it. Those rules match `secret` and `token` but not `session`, and work only if "Use Default Scrubbers" is on.

**The fix needs no SDK upgrade.**
- `@sentry/core` 10.76.2 accepts an explicit `dataCollection` (`types/datacollection.d.ts`; only `queues` is missing), and `httpIntegration` accepts `maxIncomingRequestBodySize`.
- sentry-python 2.72 accepts `include_local_variables`, `max_request_body_size` and `before_send_transaction`.

## 3. The shared contract

Both apps declare the same lists as flat string arrays. A test holds them equal (§5).

```text
HEADER_ALLOWLIST    user-agent, referer, content-type, accept, host
QUERY_DENY_TERMS    code, state, token, key, secret, session, sid, passw, pwd,
                    credential, csrf, xsrf, jwt, bearer
SCRUB_EXTRA_KEYS    access_token, access_token_ct, oauth_state, oauth_code, session_id, email
FILTERED            "[Filtered]"
```

The query terms match parameter names as substrings. They leave the app's own `mode`, `sort`, `page` and `auth` (the sign-in outcome) readable.

Every event, error or transaction, follows these rules:

1. **Request headers:** only allow-listed names survive, compared case-insensitively and exactly. The `referer` value goes through rule 3.
2. **Request identity:** `request.cookies`, `request.data`, `request.env` and `user.ip_address` are deleted, along with the existing `user.email`.
3. **Query values:** a parameter whose name contains a `QUERY_DENY_TERMS` term keeps its name, and its value becomes the literal `[Filtered]`. Parsing is a plain split on `&` and the first `=`, never URL-encoding, so both apps write the same text. The rule applies in:
   - `request.query_string`, as a string, object or pair list;
   - the query part of `request.url` and of the `referer` value;
   - `contexts.nextjs.request_path`;
   - the URL-like keys of `contexts.trace.data` and `spans[].data` (`http.target`, `http.url`, `url.full`, `url.query`, `http.query`);
   - `breadcrumbs[].data` `url`, `from` and `to`.
4. **Span header attributes:** in `contexts.trace.data` and `spans[].data`, every `http.request.header.*` key whose header name is not exactly allow-listed is deleted. So are every cookie attribute and `http.request.body.data`.
5. **Existing scrubbing:** `SCRUB_EXTRA_KEYS` are still removed from `extra` and `contexts`.
6. **No frame variables** reach Sentry from either app.

**The scrubbers fail closed and never raise.** A crashing hook makes both SDKs drop the event, which would silence the narrative-outage alert. Each rule runs in its own guard. A section that is the wrong type, or whose rule fails, is deleted rather than skipped.

## 4. Design

### 4.1 Frontend (`frontend/src/observability/`)

`scrub.ts` exports the three lists as `string[]`. The SDK's `CollectBehavior` needs mutable arrays, and the drift guard parses flat literals. Any `Set` is derived from the arrays. It also exports one data-collection constant, which every `Sentry.init` uses in place of `sendDefaultPii: false`:

```ts
type DataCollection = NonNullable<Parameters<typeof Sentry.init>[0]["dataCollection"]>;

export const SENTRY_DATA_COLLECTION: DataCollection = {
  userInfo: false,
  cookies: false,
  httpHeaders: {
    request: { allow: HEADER_ALLOWLIST },
    response: { allow: HEADER_ALLOWLIST },
  },
  httpBodies: [],
  urlQueryParams: { deny: QUERY_DENY_TERMS },
  graphQL: { document: false, variables: false },
  genAI: { inputs: false, outputs: false },
  databaseQueryData: false,
  stackFrameVariables: false,
};
```

- **What the constant controls at the source:**
  - `cookies: false` stops cookie collection in RequestData and in the span attribute copy.
  - `httpHeaders` governs the span copy, with a substring allow-list that keeps disallowed header names but sets their values to `[Filtered]`.
  - Rule 4 then removes those names.
- **v1.0.18:** the constant carries into Sentry 11, with `queues: false` added.
- **`scrubEvent`:** becomes `<T extends Event>(event: T) => T` and enforces §3 on every event. Each runtime passes it as both `beforeSend` and `beforeSendTransaction`.
- **`sentry.server.ts`** also passes:

```ts
integrations: [Sentry.httpIntegration({ disableIncomingRequestSpans: true, maxIncomingRequestBodySize: "none" })]
```

  This replaces the Next.js init's default `Http` integration by name with the same setting plus no body capture. `httpBodies` alone doesn't stop it in 10.76.2. The edge runtime has no Node HTTP server.
- **What goes:** `SCRUB_HEADER_NAMES` and the deny-list `scrubHeaders` give way to the allow-list. `scrubObject` stays for `extra` and `contexts`.
- **Replay:** unchanged. Masking stays default-on, and replay does not read `dataCollection`.
- **PostHog:** `posthog.ts` adds `disable_session_recording: true`. Sentry Replay is the app's masked replay tool. The privacy page's cookie list gains the PostHog cookie, `ph_<project key>_posthog`.

### 4.2 Backend

- **`app/observability/sentry.py`, `init_sentry`:**
  - Add `include_local_variables=False`, `max_request_body_size="never"` and `before_send_transaction=scrub_event`.
  - Still pass neither `send_default_pii` nor `data_collection`. In 2.72, passing `data_collection` switches on permissive defaults and drops the EventScrubber.
- **`scrub_event`** enforces §3 rules 1 to 5:
  - The header allow-list, and deleting `request.cookies`, `request.data`, `request.env` and `user.ip_address`.
  - Query filtering of `request.query_string` (stored percent-decoded), `request.url`, the URL-like trace and span data keys, and breadcrumb URLs.
  - Removing span header attributes.
  - The existing `user.email` and `extra`/`contexts` handling. `_SCRUB_HEADER_NAMES` remains only as the set of header-like keys that recursion drops.
- **`app/db/engine.py`:** `create_async_engine(..., hide_parameters=True)`, so database error messages carry no bound values.
- **Version cap:**
  - `pyproject.toml` caps `sentry-sdk[fastapi]>=2.66.0,<3`; `uv lock` (no upgrade) regenerates `uv.lock`, which CI checks.
  - `.github/dependabot.yml` ignores sentry-sdk majors, as for openai and SQLAlchemy. A lock refresh after sentry-python 3.0 ships can't pull in its permissive defaults unnoticed.

## 5. Testing and verification

- **`scrub.test.ts`** has one case per §3 rule:
  - errors and transactions;
  - each `query_string` form;
  - `request_path`, trace data, span data, breadcrumbs and `referer`;
  - fail-closed handling of wrong-typed sections.

  A realistic signed-in transaction fixture uses dummy values throughout: cookies, `x-vercel-ip-city`, `x-vercel-oidc-token`, `x-internal-secret`, `?mode=roast&code=…&state=…`, a body and span header attributes. Only `user-agent`, the method, the path and `mode` survive readably.

- **Real SDK test:** `@sentry/core`'s own `requestDataIntegration` and header-to-span code, given `SENTRY_DATA_COLLECTION`, produces no cookie and no IP for a signed-in request.
- **List relations:** a test asserts the relations between the lists.
- **PostHog:** `posthog.test.ts` asserts `disable_session_recording: true`.

**Backend (pytest):**

## 6. Exposure response

**Before implementation:** the operator settings in §4.4.

**After production verification**, the operator acting in each dashboard, with a check after every step:

1. **Sessions:** count the rows in the production `sessions` table, show the count, then delete them all. `sessions` is a leaf table, and deleting it leaves users, analyses and share links untouched.
   - Everyone signs in again, and any stored `si_session` stops working.
   - Cost: until owners sign in again, the nightly refresh runs their saved analyses on the shared `GITHUB_TOKEN` (`app/cron/tokens.py` `APP_FALLBACK`). That adds shared-quota pressure, and the chunk can stop with a `cron rate_limit_cliff` error event for a few nights. Before deleting, check the saved-analysis count and the token's headroom.
2. **GitHub OAuth App:** **Revoke all user tokens**. Users re-authorize when they sign in again, which step 1 already requires.
3. **Rotate the app secrets:**
   - `INTERNAL_PROXY_SECRET` and `REVALIDATE_SECRET`: the same new value in both Vercel projects.
   - `CRON_SECRET`: the backend project; Vercel Cron picks it up.
   - `GITHUB_TOKEN`: a new token with the same scopes. Revoke the old one once the new one is live.
   - Redeploy both projects, then verify `/health`, an analysis, the narrator, a share toggle (which uses the revalidate secret) and the next cron run.
4. **Sentry:** delete issues BACKEND-4, BACKEND-5 and BACKEND-6, with their events.
5. **Not rotated:** `SESSION_TOKEN_ENC_KEY`. The `key` local exists only in the session code's frames, and no retained event comes from there.
6. **Left to age out:** Vercel OIDC tokens are short-lived and need no action. Stored transactions age out under Sentry's retention.

## 7. Out of scope

- **Sentry 11 (v1.0.18).** The constant in §4.1 is built to carry into it. Span streaming and `beforeSendSpan` are decided there.
- **sentry-python 3.** Not released; the cap in §4.2 holds it off.
- **PostHog beyond IP, GeoIP, recording and the cookie list.** Its page URLs carry the app's query strings, which hold no secrets.
- **The other majors**, authlib/joserfc removal and Partial Prefetching (PLAN).
