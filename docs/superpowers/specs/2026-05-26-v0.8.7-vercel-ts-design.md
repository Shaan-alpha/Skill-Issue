# v0.8.7 — `vercel.json` → `vercel.ts` migration design spec

**Status:** Designed. Implementation plan to follow under `docs/superpowers/plans/`.
**Date:** 2026-05-26.
**Author:** Claude (Opus 4.7) with Shaan.

---

## 1. Goal

Move the root project configuration from `vercel.json` to a typed `vercel.ts` exporting `VercelConfig` from `@vercel/config/v1`. Track the Vercel 2026-02-27 knowledge update that names `vercel.ts` the recommended configuration form. No behavioral change to deployments — same services, same cron, same branch-deploy filter. This is housekeeping that keeps the repo aligned with current platform conventions.

## 2. Locked scope decisions (2026-05-26)

| Decision | Choice | Why |
| --- | --- | --- |
| Files migrated | **Root `vercel.json` only** | `backend/vercel.json` is per-function static config (`maxDuration`, `memory`, one rewrite) with no logic to type. Migrating it adds surface area without value. |
| Config style | **Pure mechanical port** | Same literal content, just typed. No dynamic-config wins (env-aware paths, computed crons, deploymentEnv()-driven values). YAGNI: the current static config works. |
| Type handling | **Approach A — verify-then-augment** | Try plain `VercelConfig` first; if TSC rejects `experimentalServices`, fall back to a file-local intersection type `VercelConfig & { experimentalServices?: … }`. Cleanest code if upstream types support it; safe fallback if they don't. |
| Package location | **New root `package.json`** | Vercel resolves `@vercel/config` from project root. There is no root `package.json` today (only `frontend/package.json`). Adding one is the minimum-viable approach; alternatives (sideways `node_modules` resolution) don't work in Node. |
| Root `package.json` shape | **`private: true`, single devDep, engines pin only** | No scripts, no app code, no name/version fields beyond what's needed. Keeps the surface area at the absolute minimum. |
| Verification depth | **Build + post-merge prod smoke** | TSC clean, local `vercel build` succeeds, then post-merge prod deploy is smoke-tested via curl against the prod URL. Direct Preview deploys aren't available because `git.deploymentEnabled` blocks `feat/*` branches from auto-deploying — and bypassing that filter for testing would defeat the point of verifying the filter survived migration. Same pattern as v0.8.1 through v0.8.6. Cron-fire verification deferred to the next natural 03:00 UTC run (Sentry tells us if it breaks). |

## 3. Operating context

The current `vercel.json` is 32 lines, three top-level keys (`experimentalServices`, `crons`, `git.deploymentEnabled`), and zero runtime logic. The migration is mechanical — the value is platform-recommended-config-form alignment, not any user-facing capability. A cold agent reading this spec a month from now should immediately understand it as "we did the housekeeping move from JSON to TS that Vercel asked us to do, nothing else."

## 4. Architecture (one paragraph)

A new `vercel.ts` at repo root mirrors the current literal as a typed `VercelConfig` export. A new minimal root `package.json` declares `@vercel/config` as the sole devDep so Vercel build can resolve the import; `npm ci` runs against `package-lock.json`. A new minimal root `tsconfig.json` lets `npx tsc --noEmit` typecheck the lone TS file standalone (no JSX, no DOM lib, no project references). Root `vercel.json` is deleted. Backend `backend/vercel.json` is untouched. If TSC rejects `experimentalServices` on the plain `VercelConfig` type, a file-local intersection type is added (`type Config = VercelConfig & { experimentalServices?: Record<string, { entrypoint: string; routePrefix?: string; framework?: string }> }`) — runtime shape is documented at https://vercel.com/docs/services, so the augmentation is a transparent type-only patch with no behavioural risk.

## 6. Risks + fallbacks

- **`experimentalServices` type gap.** Every Vercel doc example for `experimentalServices` is shown in `vercel.json`; none in `vercel.ts`. The package may not yet expose this key on the `VercelConfig` type. Mitigated by the file-local intersection type (Approach A). Runtime shape is documented and stable, so the augmentation is purely a typing patch. To drop the intersection when upstream types catch up: re-run `npx tsc --noEmit -p .` against the plain `VercelConfig` and remove the alias if it passes.
- **`@vercel/config` resolution at build time.** Vercel runs build at the project root; the new root `package.json` is where it expects to resolve the import. Mitigated by the new CI typecheck step — a missing-module regression fails CI before deploy.
- **Two `package.json` files in the repo.** Modest cognitive load. Mitigated by keeping the root `package.json` to one devDep, one `private: true`, one `engines` field — no scripts, no app code. A reader immediately recognises it as tooling-only.
- **`vercel.ts` migrating an active cron entry.** The 03:00 UTC cron fires daily; a typo on `crons.path` could silently break overnight refresh. Mitigated by (a) literal copy from the current JSON, (b) Preview-deploy build output inspection (Vercel logs the parsed cron entries), (c) Sentry alerting on cron failure if the migration breaks routing.
- **`git.deploymentEnabled` regression.** A bad migration would re-enable deploys for `feat/*` branches and could flood Vercel's hobby-tier build minutes. Mitigated by literal copy + observing that the working branch (`feat/v0.8.7-vercel-ts`) does **not** auto-deploy a Preview when pushed. If Vercel produces a Preview URL for the branch, the filter regressed and we abort.
- **No Preview-deploy path for this slice.** The `git.deploymentEnabled` filter is exactly what we're testing survived, so we can't relax it to get a Preview. Verification therefore happens on prod after merge to `main` — the same pattern v0.8.1 through v0.8.6 used. Risk is bounded because the change is pure configuration with no runtime code; if prod deploy fails, rollback is a one-commit revert.

## 8. Test plan

This slice has no runtime code paths to unit-test — `vercel.ts` is data. Verification is type-level + build-level + deploy-level:

- **Type-level (binding).** `npx tsc --noEmit -p .` at repo root passes. Wired into CI so regressions fail pre-merge.
- **Build-level (optional).** Local `vercel build` if the CLI is installed; otherwise the CI build step (`npm run build` on the frontend) and Vercel's own build during deploy serve the same role.
- **Deploy-level (binding).** Post-merge prod auto-deploy renders all five smoke-test surfaces from §7.
- **Branch-filter verification (binding).** The `feat/v0.8.7-vercel-ts` branch itself, post-push, must NOT auto-deploy a Preview. If it does, the `git.deploymentEnabled` block regressed and we abort the slice.

No new unit tests. No new vitest cases. CI's new typecheck step is the persistent guard.

## 9. Out of scope

- **`backend/vercel.json` migration.** Deferred indefinitely — no logic to type.
- **Dynamic-config wins.** `deploymentEnv()`-driven cron paths, env-aware `git.deploymentEnabled`, computed `buildCommand` — all real but YAGNI. Revisit if a concrete need surfaces.
- **Centralizing the cron path constant.** Currently hard-coded in both `vercel.ts` (new) and `app/routers/cron.py`. Cross-language constant-sharing isn't worth the indirection.
- **Adding root-level dev scripts** (lint, format, test runners). Root `package.json` stays minimal.
- **Migrating to the `routes.*` helpers** for the new config. The current `vercel.json` doesn't use `rewrites`, `redirects`, or `headers` — there's nothing to migrate to those helpers.

## 10. Implementation ordering

Six tasks. The config-port (Task 2) is one commit, not three — the file is 30 lines and per-key TSC iteration is over-cautious. Doc updates (Task 5) can run in parallel with Tasks 3–4 since they touch disjoint files.

1. **Scaffold root toolchain.** Add `package.json` (private, `@vercel/config` devDep, engines pin), `tsconfig.json` (minimal, includes only `vercel.ts`), `/node_modules` to `.gitignore`. Run `npm install` to generate `package-lock.json`. Commit. *(Does not yet exercise `vercel.ts` — toolchain stand-up only.)*
2. **Port `vercel.json` → `vercel.ts` in one commit.** All three keys (`experimentalServices`, `crons`, `git.deploymentEnabled`) ported as a single literal swap. Try plain `VercelConfig` first; if TSC rejects `experimentalServices`, add the file-local intersection alias inline and re-run TSC. Delete root `vercel.json` in the same commit. `npx tsc --noEmit -p .` clean.
3. **Wire CI typecheck step.** Extend `.github/workflows/ci.yml` with `npm ci` + `npx tsc --noEmit -p .` at repo root. Commit.
4. **Branch-filter smoke.** Push `feat/v0.8.7-vercel-ts`. Confirm Vercel does NOT produce a Preview deployment notification — this verifies `git.deploymentEnabled` survived the migration. Open PR; CI must go green.
5. **Version bumps + doc updates.** One commit covering: `backend/pyproject.toml`, `app/settings.py::VERSION`, `frontend/package.json`, landing pill, results-view footer literal, README curl response, CHANGELOG `[0.8.7]`, PROGRESS_LOG entry, PLAN v0.8.7 row + populated exit-criteria checklist, `docs/DEPLOY.md` snippet + note. Run `uv lock` to sync the backend lockfile; commit it alongside.
6. **Merge → tag → release.** PR merged to main. Prod auto-deploys. Smoke-test the five surfaces from §7 on `https://skill-issue-tau.vercel.app`. Tag `v0.8.7`; push. Release workflow publishes from the CHANGELOG section.

**Reversibility:** Tasks 1–5 are all reversible via `git revert` of the offending commit. Task 2 is the highest-blast-radius step (deletes `vercel.json`); if Vercel build rejects the new `vercel.ts` at PR time, revert that one commit and the project falls back to today's state with zero downtime.
