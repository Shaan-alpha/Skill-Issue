# v0.8.0 — Polish + Observability Design Spec

**Status:** Designed. Implementation plan to follow under `docs/superpowers/plans/`.
**Date:** 2026-05-22.
**Author:** Claude (Opus 4.7) with Shaan.

---

## 1. Goal

By the end of v0.8.0 we can answer three questions in production:

1. **What broke?** Every backend exception and every frontend error reaches Sentry with enough context (request ID, user session ID, route, structured log trail) to debug without re-reproducing.
2. **What did users actually do?** Page views, the analyze submit, narrative-mode toggles, save / share / share-card actions all reach PostHog as named events. Real-user web vitals (LCP / CLS / INP) flow through the same pipe so we can finally identify the v0.7.2 LCP element on prod.
3. **Is the page accessible?** `@axe-core/cli` reports zero critical issues across every shipped route.

Nothing else lands in this slice. Cron re-ingestion, force-refresh, on-demand share-page revalidation, `vercel.json` → `vercel.ts` — each is independent and earns its own patch release (v0.8.1, v0.8.2, …).

## 2. Locked scope decisions (2026-05-22)

| Decision | Choice | Why |
| --- | --- | --- |
| Error tracking | **Sentry** (FE + BE) | Industry default. Permanent free tier: 5K errors/mo + 50 replays/mo. No trial expiry. |
| Product analytics | **PostHog** | Permanent free tier: 1M events/mo + 5K session replays + 12-month data retention. Native React + FastAPI SDKs. |
| Real-user perf metrics (RUM) | **PostHog web vitals** (via `posthog-js` autocapture) | Same 1M-events budget, 12-month retention. Captures LCP element selector + value per visitor — closes v0.7.2's "couldn't find the LCP element on prod" gap. Avoids adding Vercel Speed Insights (Hobby tier caps retention at 30 days, against user's free-free-permanent constraint). |
| Backend structured logging | **`structlog`** with JSON renderer in prod, console renderer in dev | OSS. Plays nicely with Sentry's logging integration (events get tagged with the same `request_id` that appears in the log line). |
| Accessibility tooling | **`@axe-core/cli`** invoked locally + in CI eventually | OSS. Headless-Chromium against the deployed preview URL. Zero-critical bar matches PLAN exit criterion. |
| On-voice failure pages | **`app/not-found.tsx`** + refresh of existing `app/error.tsx` | Page voice should match the rest of the product, not Next's default. v0.7.3 already replaced the generic 500 with a 422 / org-detection branch — this completes the surface. |
| Error budget definition | **Single markdown page** (`docs/OBSERVABILITY.md`) | What counts as critical vs acceptable + baseline alert intent. **No** Sentry alert-rule wiring in v0.8.0 — we don't know real error rates yet; alerts come in a v0.8.x patch. |
| Failure mode | **Fail-open everywhere** | If Sentry's SDK fails to init or PostHog can't reach its endpoint, the page must still render. Telemetry is never a correctness boundary. |
| Deferred from PLAN's v0.8.0 listing | Cron re-ingestion, manual "Force refresh" + `DELETE /me/cache/{username}`, on-demand `revalidateTag` for `/share/[slug]` ISR, `vercel.json → vercel.ts` migration | Each is independent ops or perf work — none is required for the "we can see prod" promise. Slot into v0.8.1+ patch releases. |

## 3. Architecture (one paragraph)

Two thin cross-cutting layers ship: an `app/observability/` module on the backend (structlog config, request-ID middleware, Sentry init, PII scrub hook) and a `frontend/src/observability/` module on the frontend (Sentry browser SDK init, PostHog provider + named-event helpers, web-vitals subscription). Both are loaded once at process startup — backend via FastAPI lifespan, frontend via `instrumentation.ts` (Next 16 convention) and a top-level `<ObservabilityProvider>` in `app/layout.tsx`. Existing route handlers and components gain typed event-emission helpers (`track("analyze_submitted", {...})`) but no other refactoring. Sentry + PostHog auth-related context is filled from the existing `useSession()` hook on the frontend and the existing `current_user_or_none` dependency on the backend. Tests assert: (1) PII never leaves the boundary (no GitHub access tokens, OAuth secrets, encrypted session bytes in any event body), (2) telemetry init failure does not break the page (fail-open), (3) `request_id` propagates from incoming request → all log lines → Sentry tags for that request.

## 5. Phase plan

## 6. PII contract

These fields **must never** appear in any Sentry event or PostHog event body:

- `access_token`, `access_token_ct` (encrypted ciphertext is still treated as sensitive)
- `oauth_state`, `oauth_code`
- `session_id` (raw; the SHA256 of it is fine if needed for correlation)
- `Cookie` / `cookie` headers (full request/response cookie strings)
- `Authorization` header (full bearer values)
- GitHub OAuth client secret (env var, never logged anyway)
- Encryption keys (env var, never logged anyway)
- Email addresses (GitHub OAuth optionally returns these — we don't store them, but Sentry's User context auto-fills `email` if it's in the request envelope; force-empty)

The frontend has an equivalent list — strip from `event.request.headers` and `event.user` before send. Tests verify each field is stripped.

## 7. Identifier contract

For correlation across tools without leaking PII:

- **Anonymous viewer:** PostHog's auto-generated distinct ID. No `identify()` call.
- **Signed-in viewer:** `posthog.identify(sessionId)` where `sessionId` is the same opaque server-side session ID already in the `si_session` cookie. The session ID is **not** the GitHub login — it's a 32-byte random token. Safe to use as a Sentry user ID too.
- **Backend `request_id`:** UUID4 generated by the middleware. Returned in `X-Request-ID` response header. Echoed in every structured log line for that request and tagged on every Sentry event.

The frontend can correlate a failed request to a backend log by reading the `X-Request-ID` response header and either logging it client-side or attaching it to a Sentry breadcrumb.

## 8. Settings + secrets

New env vars (all optional — observability fails open if absent):

| Var | Where | Default | Notes |
| --- | --- | --- | --- |
| `SENTRY_DSN` | Backend | unset | Backend Sentry project DSN. Server-only. |
| `NEXT_PUBLIC_SENTRY_DSN` | Frontend | unset | Frontend Sentry project DSN. Must be `NEXT_PUBLIC_` so the browser SDK can read it at runtime. Public-by-design; Sentry DSNs are not secret. |
| `SENTRY_ENVIRONMENT` | Both | `"development"` | Set to `"preview"` on Vercel previews, `"production"` on prod. The frontend reads this via Next.js — at build time on Vercel, `NEXT_PUBLIC_VERCEL_ENV` is also available and we'll prefer that when present. |
| `SENTRY_TRACES_SAMPLE_RATE` | Both | `0.1` | 10% trace sampling. Stays well inside the 10K performance units/mo free tier. |
| `NEXT_PUBLIC_POSTHOG_KEY` | Frontend | unset | Public project key — `phc_` prefix. Safe in the bundle. |
| `NEXT_PUBLIC_POSTHOG_HOST` | Frontend | `"https://us.i.posthog.com"` | Default to PostHog Cloud US. |
| `LOG_LEVEL` | Backend | `"INFO"` | Override to `"DEBUG"` locally if needed. |
| `LOG_FORMAT` | Backend | `"json"` | Override to `"console"` locally. |

All keys provisioned to Vercel Preview + Production as Sensitive vars. Local dev uses `.env.local` (gitignored).

## 9. Testing strategy

- **Unit tests cover:** structlog config (JSON vs console), request-ID propagation across nested calls, Sentry scrub hook strips every PII field listed in §6, fail-open when `sentry_dsn` is absent, typed event helpers reject malformed payloads.
- **Integration test:** middleware sets `X-Request-ID` on the response; same UUID appears in a structlog line emitted by the route handler.
- **Mocking strategy:** Sentry SDK mocked via `sentry_sdk.transport.HttpTransport` substitute that captures envelope events; PostHog mocked via `posthog.api_key = None` (which makes the SDK drop events) + a thin wrapper around `track()` that captures call args.
- **Frontend test:** `@axe-core/cli` baseline + post-fix runs committed as the measurement doc. PostHog event emission verified via the SDK mock pattern already used by the existing vitest suite.
- **No CI integration of axe** in v0.8.0 — the run is manual against a preview deploy. CI integration deferred to a v0.8.x patch when we have a working preview-URL CI hook.

## 12. Known imprecisions

1. **PostHog event-name conventions aren't standardized in the codebase yet.** This spec proposes snake_case names (`analyze_submitted`, not `analyzeSubmitted`). If we later add server-side PostHog events from the backend, both sides should agree on the same casing — capture this in `docs/OBSERVABILITY.md` so it stays consistent.
2. **PostHog's `enable_web_vitals_autocapture` is a relatively new SDK option** (added late 2025). If it turns out to be unreliable, fallback is `web-vitals` npm package piped manually into `posthog.capture()` — minor refactor, same dashboard surface.
3. **Sentry's `tracesSampleRate: 0.1`** is a guess. Free tier on Sentry is 10K performance units/mo; at our current traffic 10% should be safe with headroom. Worth reviewing after the first week of live data.
4. **Frontend version-string update path is manual.** The landing pill + results footer literal `v0.8.0` strings come from a two-file edit that's bitten us twice (v0.7.0 had stale `v0.5.0` text). v0.8.x patches will tighten this with a single source of truth — out of scope here.
