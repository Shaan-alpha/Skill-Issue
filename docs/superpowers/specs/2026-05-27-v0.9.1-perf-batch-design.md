# v0.9.1 — `/me/analyses` N+1 fix + Layer A cache schema version design spec

**Status:** Designed. Implementation plan to follow under `docs/superpowers/plans/`.
**Date:** 2026-05-27.
**Author:** Claude (Opus 4.7) with Shaan.

---

## 1. Goal

Two small, independent perf/correctness patches batched per the 2026-05-26 v0.9.x decomposition:

1. **Eliminate the N+1 `SELECT AnalysisRun` in `/me/analyses`.** The list endpoint currently issues one `SELECT` for the page of analyses, then N additional `SELECT AnalysisRun` calls (one per row) inside the serializer. With 20 rows per page that's 21 round-trips when 1 would do.

2. **Add a `REPORT_SCHEMA_VERSION` constant to the Layer A cache key.** Today's global `KEY_PREFIX = "si:v1:"` is the only invalidation hatch — bumping it nukes every namespace (GH responses, narratives, locks, budgets, rate-limit counters). Per-namespace versioning lets a future `Report`-shape change invalidate the report cache without 6h of cross-namespace noise.

Both are tiny (~5 LOC each), independent, and naturally pair as a "perf batch" patch.

## 2. Locked scope decisions (2026-05-27)

| Decision | Choice | Why |
| --- | --- | --- |
| N+1 fix mechanism | **Surface the already-joined tuple from `list_user_analyses`** | The existing query already does `select(Analysis, aliased(AnalysisRun))` with the right join — it just discards the join result. Smaller blast radius than adding a `latest_run` relationship + `selectinload`. |
| Return-type change | `tuple[list[Analysis], int]` → `tuple[list[tuple[Analysis, AnalysisRun \| None]], int]` | Explicit at the type level. Caller updates are mechanical (one route, two DB-fixture tests). |
| Cache version scope | **Per-namespace `REPORT_SCHEMA_VERSION` constant** | Bumping it invalidates only the report namespace. Per PLAN.md's v0.9.0 audit-carryover item. |
| Cache key shape | `si:v1:report:v1:octocat` | KEY_PREFIX + namespace + schema_version + username. One additional path segment, zero change to existing `KEY_PREFIX`. |
| Initial schema version | **`1`** | Today's Report shape is the v1 baseline. Future bumps come on actual shape changes. |
| Test verification | (a) DB-fixture test asserts new tuple shape; (b) new unit test on `report_key` asserts shape + bump-rewrites-key | Cache test is pure unit (no DB needed). N+1 verification rides on the existing DB-fixture tests plus the type-level signature change. |

## 3. Operating context

The N+1 is currently invisible in dev (one user → one row in `/me/analyses` → no extra queries). It surfaces at scale: users with N saved analyses pay `1 + N` DB round-trips per page load. At 20-per-page and Neon's ~10ms baseline latency, that's ~200ms wasted on a route that should be ~20ms. The fix is mechanical because the join was already there; this slice is closing a known oversight.

The cache versioning patch is preemptive. No `Report` shape change is queued, but every previous shape change (v0.7.0, v0.7.5, v0.8.0) silently invalidated keys via Pydantic deserialization warnings against the 6h-TTL'd entries until they aged out. A schema-version suffix turns those silent ~6h warning storms into a clean cache-miss-cliff on deploy.

## 4. Architecture (one paragraph)

**Patch 1 — N+1 fix.** `app/persistence/analyses.py::list_user_analyses` changes its return statement from `[r.Analysis for r in rows], int(total or 0)` to `[(row[0], row[1]) for row in result], int(total or 0)`, surfacing both halves of the already-joined `Row[Analysis, AnalysisRun]`. The type signature updates to `tuple[list[tuple[Analysis, AnalysisRun | None]], int]`. The sole caller `app/routers/me.py::my_analyses` updates `for a in rows:` → `for a, run in rows:` and deletes the inner `await db.scalar(select(AnalysisRun).where(AnalysisRun.id == a.latest_run_id))` line. Net: one query per page instead of `1 + N`.

**Patch 2 — Cache schema version.** `app/cache/keys.py` gains `REPORT_SCHEMA_VERSION = 1` constant at module top. `report_key(username)` changes from `return username.lower()` to `return f"v{REPORT_SCHEMA_VERSION}:{username.lower()}"`. Composed key shape under `RedisCache._build_key`: `si:v1:report:v1:octocat`. Existing pre-bump keys (`si:v1:report:octocat`) are never read again — they orphan in Redis until their 6h TTL expires.

### 5.2 New files

| File | Responsibility |
| --- | --- |
| `backend/tests/cache/test_keys.py` (new file) — or new test in existing `tests/test_report_cache.py` if it exists; pick at implementation time | Two unit tests: (a) `report_key("Octocat")` returns `"v1:octocat"` (lowercases + prefixes); (b) bumping `REPORT_SCHEMA_VERSION` (via monkeypatch) produces a different key for the same username. |

### 5.3 Untouched

- `app/cache/client.py::KEY_PREFIX` — still `"si:v1:"`, still the global escape hatch. Per-namespace versioning is additive, not a replacement.
- All other cache key builders (`rate_limit_key`, `narrative_key`, `budget_day_key`) — Report is the only one with a fluid Pydantic-validated shape; others are scalars or text.
- The `Analysis` model — no new `latest_run` relationship.

## 6. Risks + mitigations

- **Orphan cache entries post-deploy.** Old `si:v1:report:<username>` keys exist for up to 6h after deploy with no readers. Mitigation: none needed; they GC naturally. Redis memory impact is bounded by the active-user-count × 6h × avg-Report-size — well inside Upstash free tier.
- **DB-fixture test signature drift.** Two existing tests access `r.target_login` directly; the new tuple shape breaks them. Mitigated by updating both in the same patch (caught at plan-write time, not at execution).
- **Type-narrowing in route.** `for a, run in rows:` — `run` is `AnalysisRun | None`. Existing serializer's null-check (`if run is None else { ... }`) survives the refactor verbatim, just on the variable bound by tuple unpacking instead of by `db.scalar`'s `Optional` return.
- **Cache-key migration is non-reversible-cleanly.** If we ever bump and then need to revert, the old keys are gone (they aged out at 6h). Mitigation: schema version bumps go in version-controlled commits; revert is "just deploy the old version and re-warm".

## 8. Test plan

**Patch 1 (N+1).**
- Existing DB-fixture tests `test_list_user_analyses_sorts_by_latest_run_desc` + `test_list_user_analyses_sort_score_desc` updated to unpack the new tuple shape. They continue to validate sort order against the joined `AnalysisRun`.
- No new query-counter test. Justification: the only way the N+1 returns is for someone to re-add a `db.scalar(select(AnalysisRun)...)` call inside the route loop. The type signature change to `list[tuple[Analysis, AnalysisRun | None]]` makes that re-addition mechanically harder (the `run` is already in hand). Query-counter tests are high-overhead infrastructure to guard against a regression that the type system already discourages.

**Patch 2 (cache).** Two new pure-unit tests in `tests/cache/test_keys.py` (or extension of an existing cache-keys test if discovered at implementation):

```python
def test_report_key_includes_schema_version():
    assert report_key("Octocat") == "v1:octocat"

def test_report_key_bump_rewrites_namespace(monkeypatch):
    from app.cache import keys as keys_module
    monkeypatch.setattr(keys_module, "REPORT_SCHEMA_VERSION", 7)
    assert report_key("octocat") == "v7:octocat"
```

Both run as pure unit tests (no DB, no Redis), inside the standard pytest non-DB-fixture suite.

## 9. Out of scope

- **`latest_run` relationship on `Analysis` model.** Approach considered + rejected in §2 (Option Y). Reach for it if a second caller wants the same data.
- **Per-namespace versioning for caches other than report.** GH responses are GitHub's contract (no shape changes from our side), narratives are opaque text, lock/budget/rate-limit are scalars. Nothing else has a versioning need today.
- **Cache key migration tooling.** No SCAN-and-delete of old `report:<username>` keys. They GC at TTL; manual purge would burn a feature slice for ~6h of memory savings.
- **Frontend changes.** The `/me/analyses` response shape is unchanged. The N+1 fix is purely a backend perf patch; the JSON contract is identical.

## 10. Implementation ordering

Four tasks. Patch 1 and Patch 2 are independent and could ship as separate slices — batching them is a pragmatic choice for the v0.9.x rhythm.

1. **Patch 2 first (cache).** Pure unit test, no DB dependency, no other code touches it. Write `test_report_key_includes_schema_version` (red — function returns `username.lower()` not `v1:...`), implement the change, run test (green), commit. Then write `test_report_key_bump_rewrites_namespace`, run (should pass on first try since the function already reads the constant), commit if separate or amend.
2. **Patch 1 (N+1).** Update `list_user_analyses` return type + impl. Update `my_analyses` route. Update the two DB-fixture tests inline. Run full test suite — DB-fixture tests skip locally without `TEST_DATABASE_URL`, but the non-DB suite must stay green. Commit.
3. **`ruff check` + `ruff format --check`.** Address any lint/format issues from either patch. Commit any fixups.
4. **Doc ritual + ship.** Version bumps across the 8 file-literal spots (matching v0.9.0's exact list). CHANGELOG `[0.9.1]`. PROGRESS_LOG entry. PLAN row flip. `uv lock`. Push. CI green. Merge. Prod smoke. Tag. Release.

**Reversibility.** Both patches are independently revertable via `git revert` of the offending commit. The cache change is non-reversibly-cleanly in the sense that revert leaves orphan `v1:` keys until TTL — same shape of acceptable cost as the deploy itself.
