# v0.8.2 — Manual "Force refresh" design spec

**Status:** Designed. Implementation plan to follow under `docs/superpowers/plans/`.
**Date:** 2026-05-22.
**Author:** Claude (Opus 4.7) with Shaan.

---

## 1. Goal

A signed-in user on `/me` can click a small Refresh button next to any of their saved analyses and get a fresh re-ingest **right now** instead of waiting for tonight's v0.8.1 cron. The new Report writes a fresh `analysis_runs` row, write-throughs the v0.7.0 Layer A cache, and shows the updated score inline within ~5-10 seconds.

This is a complement to v0.8.1, not a replacement. The cron handles bulk overnight freshness; this slice handles the impatient case ("I just pushed to this repo, refresh it now").

## 2. Locked scope decisions (2026-05-22)

| Decision | Choice | Why |
| --- | --- | --- |
| Semantic | **Synchronous refresh-and-persist** | Users expect "refresh" to mean "give me new data NOW". Invalidate-only (PLAN.md's original DELETE wording) leaves the cache empty and forces a second click. Synchronous is one click, one wait, one new score. |
| Method + path | **`POST /me/refresh/{username}`** | POST because we mutate persistent state (a new `analysis_runs` row). `/me/refresh/...` keeps it scoped to the requesting user — distinct from the anonymous-readable `GET /analyze/{username}`. |
| Ownership check | **Strict — must be in user's saved `analyses`** | Force-refresh is a `/me`-page action. Refusing 404 on unsaved targets prevents the route from becoming a back door to bypass the global `GET /analyze` cache. Saving the analysis first is one extra click — trivial. |
| Rate limiting | **Per-user 10/hour cap, INCR + TTL on Upstash** | Cheap (~30 lines), reuses v0.7.0 cache infra. Generous enough that normal use never hits it; tight enough that a single user can't burn 1000 GH calls in a minute. v0.9.0 will add global IP-level limits; this is the per-user complement. |
| Token strategy | **Requesting user's session token directly** | Simpler than cron's resolver — the user is signed in and IS the owner. Use `session.access_token` from the `require_session` dependency. App-token fallback isn't needed since session is required. |
| Concurrent refreshes (same target, different users) | **Lean on Layer B singleflight** | Already in place from v0.7.0. Two users force-refreshing `octocat` at the same moment coalesce into one GH fetch; both get the same fresh Report. No new code. |
| Cache TTL after force-refresh | **Standard 6h Layer A TTL** | Don't extend specially — cron will refresh again tonight regardless. Uniform TTL keeps the cache model simple. |
| PostHog event | **`force_refresh_clicked`** with `{target_login, duration_ms, success}` | Same naming convention as the v0.8.0 named events. `target_login` is public, not PII. |
| Out of slice | Bulk "refresh all" button, cross-user invalidation hooks, Sentry alert wiring | Each is independent. YAGNI applied for the 100-users/day operating ceiling. |

## 3. Operating context (2026-05-22)

Skill Issue is pre-alpha with expected traffic of ~100 users/day max through public launch. The rate limit and singleflight design are insurance against malicious abuse, not load. At normal scale the route will idle.

## 4. Architecture (one paragraph)

A new `POST /me/refresh/{username}` route in `app/routers/refresh.py`. The handler chain: `require_session` dependency resolves the signed-in user → ownership helper `get_user_analysis_by_target(db, user.id, username)` returns `None` → 404 → otherwise rate-limit gate via `try_increment_force_refresh_counter(cache, user.id)` (Upstash `INCR` on a key keyed by `user_id` + UTC-hour bucket, TTL 3700s) → returns `(allowed, current_count)`; on `not allowed`, 429 with `Retry-After` set to seconds remaining in the hour → otherwise delete the Layer A `report:` key for `username.lower()` → call the existing `get_report_for_user(username, session)` pipeline (which runs cold because we just cleared the cache, write-throughs Layer A, and respects singleflight if a concurrent refresh of the same target is in flight) → call `record_run` with the fresh Report → return the Report inline (200, same shape as `GET /analyze/{username}`). The frontend `/me` page adds a `RefreshCw` button per grid row; state machine is `idle → pending → success | error`. Pending state disables the button and shows a small spinner; success animates the new score in and toasts the duration; error toasts the message and re-enables the button. Every click fires the PostHog `force_refresh_clicked` event with `target_login`, `duration_ms`, and `success` properties.

## 6. Data flow

1. User clicks the Refresh button on a `/me` grid row.
2. Frontend dispatches `POST /me/refresh/{target_login}` with the existing session cookie. UI flips to `pending`.
3. Backend `require_session` resolves the user (else 401).
4. `get_user_analysis_by_target(db, user.id, target_login)` returns the row (else 404).
5. `try_increment_force_refresh_counter(cache, user.id)` returns `(False, _, seconds_remaining)` → 429 with `{detail: "rate_limited", retry_after_seconds: N}` and `Retry-After: N` header. Else `(True, _, _)`.
6. `await cache.delete(NAMESPACE_REPORT, report_key(target_login))` — best-effort, ignore errors.
7. `report = await get_report_for_user(target_login, session=resolved_session)` — runs cold, writes Layer A.
8. `await record_run(db, analysis_id=analysis.id, ...)` — same payload shape as the GET handler.
9. Return `200 + Report.model_dump_json()`.
10. Frontend receives the Report, updates the row's displayed score/tier/last-refreshed timestamp, toasts duration, fires `force_refresh_clicked` with `{target_login, duration_ms, success: true}`.

## 7. Error contract

| Code | Body | When |
| --- | --- | --- |
| 401 | `{"detail": {"error": "auth_required"}}` | No `si_session` cookie or session expired. |
| 404 | `{"detail": "no_saved_analysis"}` | User has no row in `analyses` with this `target_login`. |
| 404 | `{"detail": "GitHub user '<login>' not found"}` | Bubbled from existing pipeline. |
| 400 | `{"detail": "Invalid GitHub username"}` | Bubbled from `_USERNAME_RE` check in `get_report_for_user`. |
| 422 | `{"detail": "'<login>' is a GitHub organization..."}` | Bubbled from v0.7.3 org-detection. |
| 429 | `{"detail": "rate_limited", "retry_after_seconds": N}` + `Retry-After: N` header | 11th call in the current UTC hour. |
| 502 | `{"detail": "GitHub API error: <status>"}` | Bubbled from existing pipeline. |
| 500 | `{"detail": "Failed to analyze user '<login>'"}` | Bubbled. |

## 8. Rate-limit key shape

```
si:v1:rate_limit:force_refresh:<user_id>:<YYYY-MM-DD-HH>
```

- Bucket boundary is UTC-hour. `hour_bucket` resets every wall-clock hour rollover, not via sliding window — simpler, slightly leakier (a user could fire 10 at 14:59 + 10 at 15:00 = 20 in two minutes). Acceptable at 100 users/day.
- INCR is atomic; we set the value's TTL to 3700s on first observation so the key auto-cleans up well after the bucket expires.
- Limit (10) lives in `Settings.force_refresh_per_user_per_hour: int = 10` — env-overridable.

## 9. Test strategy

Five layers:

1. **Auth boundary.** No cookie → 401. Expired cookie → 401.
2. **Ownership.** Signed-in user requests refresh of a target they never saved → 404. Same user requests their actually-saved target → proceeds.
3. **Rate-limit.** With limit=10: first 10 succeed, 11th returns 429 with `Retry-After` header populated. Re-run after monkey-patched clock advance puts the user in a new hour bucket → succeeds again.
4. **Happy path.** Mocked GH pipeline returns a stub Report. Assert: Layer A cache `report:<lowercase>` is populated post-call (via FakeRedis inspection), a new `analysis_runs` row is in the DB, response shape matches `Report` schema.
5. **Cache delete is fail-open.** If the `cache.delete` raises (FakeRedis fault injection), the route still proceeds to live ingest — same fail-open posture as the rest of the cache layers.

Frontend:

6. Button click triggers POST with correct path; pending state visible during the call.
7. 200 response updates the displayed score; PostHog `force_refresh_clicked` fired with `success: true`.
8. 429 response shows "Rate limit — try again in N min" toast; PostHog event fired with `success: false`.

## 10. Exit criteria

- [ ] `POST /me/refresh/{username}` without cookie → 401.
- [ ] Signed-in user requests target they never saved → 404 `no_saved_analysis`.
- [ ] 11th call in the same UTC hour returns 429 with populated `Retry-After` header.
- [ ] Happy path: returns the Report JSON, writes a new `analysis_runs` row, populates Layer A.
- [ ] Cache delete failure doesn't break the route (fail-open verified by FakeRedis `fail_next` injection).
- [ ] `/me` grid renders a Refresh button per row; click cycles through pending → success.
- [ ] PostHog `force_refresh_clicked` event fires with `{target_login, duration_ms, success}`.
- [ ] `docs/OBSERVABILITY.md` documents the new event.
- [ ] `CHANGELOG.md` + `docs/PROGRESS_LOG.md` updated; version bumped to `0.8.2`.

## 11. Provisioning gate

**None.** Reuses existing infra:

No new env vars, no new accounts.

## 12. Out of scope

- **Bulk "refresh all" button.** Could land in a v0.8.x patch if real demand surfaces. At 100 users/day, individual refreshes are sufficient.
- **Cross-user invalidation events.** Layer A cache is already keyed by `target_login`; user X's force-refresh of `octocat` warms it for user Y's saved `octocat` automatically. No webhook needed.
- **Sentry alerting on force-refresh failures.** Deferred to the v0.8.x patch that wires alert rules globally.
- **Cache TTL extension for force-refreshed entries.** Uniform 6h TTL — cron handles overnight freshness.
- **Persisting `last_force_refreshed_at` on `analyses`.** The latest run's `ingestion_completed_at` already captures this — same column the v0.8.1 cron query relies on.
