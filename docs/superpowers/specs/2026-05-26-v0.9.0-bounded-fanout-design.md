# v0.9.0 — Bounded GitHub fan-out design spec

**Status:** Designed. Implementation plan to follow under `docs/superpowers/plans/`.
**Date:** 2026-05-26.
**Author:** Claude (Opus 4.7) with Shaan.

---

## 1. Goal

Cap concurrent GitHub API calls inside `ingest_profile` to a configurable limit (default 8) so a single analysis can't burst past the per-token rate-limit budget, and so anonymous-token sharing scales to more analyses/hr before the 5000/hr GitHub ceiling bites.

This is the first slice of the v0.9.x Beta hardening family (decomposed 2026-05-26: bounded fan-out → /me N+1 + cache schema version → DB pool tune → rate limiting + abuse → security review + load test → legal docs). Each slice is shippable in isolation.

## 2. Locked scope decisions (2026-05-26)

| Decision | Choice | Why |
| --- | --- | --- |
| Cap mechanism | **Per-call `asyncio.Semaphore` via `_gated` helper** | Approach A; minimum blast radius. Constrains *only* the ingestion fan-out, not every `GitHubClient` call. |
| Cap value source | **`Settings.gh_ingest_concurrency: int = 8` (env override `GH_INGEST_CONCURRENCY`)** | Matches the v0.8.x settings pattern (`narrative_daily_limit`, `force_refresh_per_user_per_hour`). Tunable without redeploy if the cap turns out wrong in prod. |
| Default cap | **8** | Per PLAN.md. Gives ~6.25× breathing room vs the projected ~125 analyses/hr ceiling at 5000 GH calls/hr. |
| Sequential `list_languages` loop | **Left as-is** | Already bounded (1 in-flight by construction). Parallelizing it would *increase* peak concurrent for the same total cost — counter to v0.9.0's goal of reducing burst. Latency optimization is a separate, post-v1.0 concern. |
| Fan-out points bounded | **Both `asyncio.gather` blocks in `profile.py`** | (1) `_enrich_repo_signals` × ≤20, (2) `list_commits` × ≤10. The only true concurrency points today. |
| Semaphore instance | **One per `ingest_profile` invocation** | No global state. The two gather blocks run sequentially (block 1 fully completes before block 2 starts), so the same semaphore is reused with no cross-block contention. |
| Test shape | **Instrumented fake `GitHubClient` records max in-flight; assert ≤ cap** | Satisfies PLAN.md's "verified by integration test against a 50-repo profile" exit criterion AND lets us assert the cap is actually enforced (which an end-to-end test alone can't observe). |

## 3. Operating context

Today's `ingest_profile` issues these concurrent bursts per analysis on a profile with ≥20 non-fork repos:
- **Block 1** ([profile.py:143](../../backend/app/ingestion/profile.py#L143)): up to 20 simultaneous `GET /repos/{owner}/{repo}/contents` calls via `_enrich_repo_signals`.
- **Block 2** ([profile.py:179](../../backend/app/ingestion/profile.py#L179)): up to 10 simultaneous `GET /repos/{owner}/{repo}/commits` calls (top 10 non-fork repos × author=username × since=2-years-ago).

Peak burst: **30 concurrent requests**. At ~125 analyses/hr against the 5000/hr per-token ceiling, this number — when combined with the existing sequential `list_languages` loop's separate budget consumption — exhausts the budget faster than expected and produces 403 cliffs that the v0.8.4 narrative-provider-honesty fix surfaced indirectly via Sentry.

Bounding both gather blocks at 8 concurrent doesn't change *total* call count (one analysis still makes ~30+ GH calls), but it spreads them over time so the per-second burst can't trip GitHub's secondary rate limits — which fire at sustained-burst thresholds before the primary 5000/hr cap.

## 4. Architecture (one paragraph)

A new file-local helper `async def _gated(sem: asyncio.Semaphore, coro: Awaitable[T]) -> T` wraps any coroutine in `async with sem`. Inside `ingest_profile`, one `asyncio.Semaphore(settings.gh_ingest_concurrency)` is constructed at entry. Both existing `asyncio.gather` call-sites change from `gather(*(coro for r in repos))` to `gather(*(_gated(sem, coro) for r in repos))`. The semaphore is local-to-call so concurrent `ingest_profile` invocations (e.g., two users analysing different targets at once) each get their own independent cap — the global GH-call rate is the sum of however many analyses are in flight. This is intentional: the cap is about per-analysis burstiness, not global throttling. Global throttling lives in v0.9.3 (rate limiting).

## 6. Risks + mitigations

- **Tail latency degrades on heavy profiles.** Capping at 8 means a 20-repo enrich takes `ceil(20/8) × avg_latency ≈ 3 × avg_latency` instead of `1 × avg_latency` in the unbounded case. Worst case adds ~500ms to a cold analysis. Mitigated by: (a) Layer A cache absorbs the latency cost — first hit pays it once, subsequent hits within 6h are sub-200ms regardless; (b) RUM via PostHog (v0.8.0) will surface real-user impact if it's worse than expected; (c) cap is env-tunable post-deploy.
- **Semaphore exhaustion deadlock.** None. `_gated` releases the semaphore on coroutine exit (exception-safe via `async with`). No nested acquires inside fan-out coros (the wrapped coros only make a single GH request each, then return).
- **Backwards compatibility of the new settings field.** It's optional with a default; existing deployments without `GH_INGEST_CONCURRENCY` set will transparently use 8.
- **Test fragility against future `profile.py` refactors.** The instrumented-`FakeGitHubClient` test asserts max-in-flight, which is a contract about *what the semaphore guarantees*, not about *which method is wrapped*. Refactors that move the fan-out elsewhere would still need to honor the contract — the test stays meaningful.

## 8. Test plan

Two new tests added to the existing `backend/tests/test_ingestion.py`:

**Test 1 — default cap honored.**

```python
async def test_bounded_fanout_default_cap(monkeypatch):
    fake = FakeGitHubClient(repos=50)  # synthetic 50-repo profile fixture
    await ingest_profile("octocat", fake)
    assert fake.max_in_flight <= 8, f"expected ≤8 in-flight, got {fake.max_in_flight}"
    assert fake.total_calls >= 30  # sanity: the test actually drove enough load
```

**Test 2 — overridable via settings.**

```python
async def test_bounded_fanout_overridable_cap(monkeypatch):
    monkeypatch.setattr("app.settings.settings", Settings(gh_ingest_concurrency=2))
    fake = FakeGitHubClient(repos=50)
    await ingest_profile("octocat", fake)
    assert fake.max_in_flight <= 2
```

`FakeGitHubClient` is a minimal stub that:
- Returns a 50-repo `list_repos` response.
- For each `get_repo_root_contents`, `list_languages`, `list_commits`, and `get_profile_readme`: increments `current_in_flight` on entry, awaits a tiny `asyncio.sleep(0.005)` to force genuine concurrency, decrements on exit, and tracks `max_in_flight = max(max_in_flight, current_in_flight)`.
- For `graphql`: returns minimal valid responses for `PINNED_REPOS` and `EXTERNAL_PRS`.
- For `get_user`: returns a non-Organization user shape.

The sleep is what makes the test meaningful — without it, asyncio could schedule fast-completing coros sequentially and the assertion would pass even without a semaphore.

## 9. Out of scope

- **Parallelizing the sequential `list_languages` loop.** Already bounded; parallelizing would expand peak concurrent, opposite of this slice's goal.
- **Per-endpoint concurrency caps.** A single global cap covers all current ingestion endpoints uniformly. Per-endpoint tuning is YAGNI until we observe an endpoint-specific bottleneck.
- **Per-token-pool dynamic cap** (e.g., raise the cap when a user-token is being used instead of the shared app token). Single hard cap suffices until real traffic patterns surface the need.
- **Adaptive backoff on 403 secondary rate-limit responses.** Already handled by `GitHubClient`'s existing 403 handling and cached-status logic.
- **Bounding the cron route's GH calls.** Cron uses the same `ingest_profile` and inherits the cap automatically; no extra work.
